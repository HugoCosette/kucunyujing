## 四、关键不变量验证（P0 级，全绿）

1. **累积下单 = 待收 + 到货** —— TC-D02/F02 通过
2. **到货不改变预计库存**（待收与到货此消彼长）—— TC-F03 通过：received 300→500，projectedStock 恒为 1000
3. **作废单不进任何统计** —— TC-D01/H01 通过：含作废单的 X 累积下单=1000（非 1500）
4. **receivedQty 由 receipts 派生**，不信任外部值 —— TC-G01 通过：外部传 999，实际归一化为 300

## 五、安全测试说明

系统为**纯前端静态应用，无后端、无数据库、无用户登录、无对外网络请求**（README 明确数据仅存浏览器内存/IndexedDB/localStorage）。因此 OWASP Top 10 中依赖服务端的类别（A01 访问控制、A02 加密失败、A07 认证、A10 SSRF 等）**不适用**。

相关面走查：
- **XSS**：用户输入（染厂名/备注/品名）通过 Element Plus 插值渲染，默认转义，无 `v-html` 直出用户数据 —— 风险低
- **数据完整性**：导入走 `inventoryImport.js` 表头识别+数值/枚举校验+错误行收集；订单归一化丢弃空白/非法行 —— 通过
- **本地存储**：IndexedDB 写失败有明确提示，不静默丢单 —— 通过

## 六、缺陷与观察项

### 缺陷（1）
- **BUG-001 [P3]** 小批量补单规则文档描述与实际配置不一致
  - 文档 §4.3：`≤50 不下单 · 51 以上每缸 60`
  - 实际 `settings.json`：`≤50 skip / 51–100 fixed60 / >100 round10`
  - 代码默认 `createDefaultVatRules()`：又是另一套（≤50 skip / 51+ ladder60）
  - 影响：need=150 时文档口径 180 公斤、实际配置 150 公斤。三处口径不一致
  - 建议：统一文档、代码默认、实际配置三者

### 观察项（非缺陷，2）
- **OBS-001 [P2]** `stores/purchase.js receiveOrder()` 无超收兜底校验，防护单一依赖 UI 弹窗。当前仅一处调用不可触发，建议补 store 层校验（amount ≤ 待收）
- **OBS-002 [P3]** 构建产物多个 chunk >500KB（index 761KB 等），性能提示，建议按需做代码分割
