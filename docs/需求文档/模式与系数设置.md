# 模式与系数设置

> 状态：已实现并验证（2026-11-04）。本文是「备货模式 → 评分档 → 系数」的**唯一口径说明**，也是交接给其他对话/Agent 的入口文档。
> **维护约定见第 14 节：任何代码改动都必须同步更新本文。**

---

## 1. 一句话概述

每个 SKU 的备货系数由三级查表得到：**模式（归属）→ 评分档（打分分档）→ 色彩类别（黑白/彩色）**。模式决定 SKU 属于哪套配置，评分档决定该 SKU 在模式内的高低评分，色彩决定同一档下取黑白还是彩色的系数。

```
导入列 → ① 模式因子匹配 → ② 评分因子打 S/A/B/C → ③ 按等级计数定档 → ④ 模式×档×色彩取系数 → ⑤ 库存与预警计算
```

---

## 2. 演进原因（旧模型为什么被替换）

| 维度 | 旧模型（已删除） | 现模型 |
|---|---|---|
| 分类层数 | 1 层：评分规格（热销A / 常规A） | 2 层：模式 + 评分档 |
| 因子来源 | 只有 4 个动销指标 | 全部导入列（10 个数值列可评级） |
| 因子条件 | 一组 AND（≥/≤） | 模式因子（AND）与评分因子（评级）分离 |
| 打分 | 无 | 每模式、每因子独立 S/A/B/C 阈值 |
| 分档 | 名称固定、顺序首个命中、兜底最后一个规格 | 按「等级计数条件」判定，档名自由 |
| 系数键 | `规格 × 色彩` | `模式 × 评分档 × 色彩` |
| SKU 关联 | 品名 + 颜色 | **唯一标识** |
| 配置保存 | 仅内存，刷新即丢 | 源文件 `src/stocking/config.json` |

删除的文件：`src/data/heatRules.js`、`src/data/stockingRules.js`、`src/utils/heatRules.js`。

## 4. 判定链（实现口径）

### 4.1 模式层

- 模式集合由 `config.rules` 给出，`isDefault: true` 的那条是「默认模式」，**固定末位**，无条件命中。
- 非默认模式要求**互斥**：一个 SKU 只属于一条模式。
- 未配置任何模式因子的非默认模式**不参与匹配**（保存时给 warning）。
- 若实际数据仍命中多条模式：运行时取模式列表中靠前的一条，并在 `item.ruleConflict = true`，主表模式列显示红色虚下划线提示。保存时弹确认框，列出冲突数与样例 SKU。
- 同字段允许多条因子表达区间（如 `订单总数 ≥ 100` + `订单总数 ≤ 199`），同一模式内全部 AND。

### 4.2 评分层

```
对模式启用的每个因子：
    value = Number(item[field])
    依次比较 S / A / B / C 的阈值（统一 ≥），取第一个满足的等级
    都不满足、值为空/非数字、或该等级未配置阈值 → Z
counts = 各等级出现次数（只统计本模式启用的因子，Z 也计数）
```

- 档位判定：按 `tiers` 顺序取第一个「全部条件都成立」的非默认档；都不成立时落到末位默认档。
- 档条件结构：`{ grade: 'S'|'A'|'B'|'C'|'Z', operator: 'gte'|'lte'|'eq', count: number }`，同档内 AND。
- 例：`[{grade:'S',operator:'gte',count:2}]` 表示「至少 2 个因子达到 S」。

### 4.3 系数层

```
coefficients = rules[ruleId].tiers[tierId].coefficients[item.category]  // {redLine, normal, peak}
红线库存 = 周消耗 × redLine
正常库存 = 周消耗 × normal
峰值库存 = 周消耗 × peak
```

`strategyAvailable`（模式是否可用）需同时满足：系数取到、`周消耗 > 0`、三系数都是有限数。否则整行按「模式缺省」：三档库存/缺口量/缺口率显示「缺省」，预警灰、库销比 `--`。

**兜底只兜「模式 + 评分档」，不兜系数**。缺省分四种，行数据上带 `strategyIssue`，主面板预警与配置页「系数」列的悬停提示会直接显示原因：

| 原因 | 单元格内短文案 | `strategyIssue`（悬停） |
|---|---|---|
| 没有命中任何模式档位 | 未命中档位 | 未命中任何模式档位 |
| `色彩` 为空 | 色彩未填 | 色彩未填写，无法确定取黑白还是彩色系数 |
| 命中档位缺该色彩那组系数 | 缺黑白系数 / 缺彩色系数 | 该评分档未配置「黑白/彩色」系数 |
| 三系数有 null | 系数未填全 | 红线 / 正常 / 峰值系数未填写完整 |
| 周消耗 ≤ 0 | 周消耗为0 | 周消耗为 0，备货库存无法计算 |
| 品名父行里有子行缺省 | 子行缺省 | 同左 |

配置页「备货策略」四列（红线库存 / 正常库存 / 峰值库存 / 系数）**不再显示「缺省」**，直接把短文案写在格子里（红色小字），悬停显示完整原因；品名父行只在有子行缺省时提示。

预警判定顺序（`src/utils/inventory.js`，未改动）：缺省灰 → `< 红线` 红 → `> 峰值` 紫 → `正常×80%~120%` 绿 → 其他黄。

### 4.4 派生字段的计算时机（重要）

模式、评分档、等级明细**不写入**库存行数据，也不在导入时快照，而是**每次渲染时按当前配置现算**：

```js
const evaluator = createEvaluator(config)      // 每次重建行数据时建一次
const row = calculateInventoryRow(evaluateItem(item, evaluator))
```

`evaluateItem` 在拷贝上完成「模式 → 档位 → 系数」整个链路，并直接带上 `stockingCoefficients`；`calculateInventoryRow` 只按 `item.category` 取黑白/彩色那一组，不再按 `ruleId + tierId` 二次查表。

原因：早期实现把 `ruleId/ruleName/tierId/tierName` 写回 `item` 作为快照，保存配置后没有回写，导致「删掉模式1后主面板仍显示模式1」；而系数靠另一份归一化结果按 id 查表，两次归一化一旦对不上（例如档位缺少 id 时各自新生成一个）就会整条模式都显示「缺省」。现在 store 只保存导入的原始数据，一次评估即得到全部派生字段。

> 不要重新引入把评估结果写回 store item 的用法，也不要再按 id 二次查系数（公开 API 只保留 `evaluateItem`）。

## 5. 配置文件结构

唯一来源：[src/stocking/config.json](/d:/Ghaniyy/Code/Demo/网布表格/kucunyujing1.1/src/stocking/config.json)

```json
{
  "version": 1,
  "updatedAt": "2026-11-04T00:00:00.000Z",
  "rules": [
    {
      "id": "rule-1",
      "name": "模式1",
      "isDefault": false,
      "factors": [
        { "field": "monthlyAvgCount", "operator": "gte", "value": 200 },
        { "field": "totalOrders", "operator": "gte", "value": 10 }
      ],
      "grades": {
        "monthlyAvgCount": { "S": 120, "A": 90, "B": 30, "C": 1 },
        "totalOrders": { "S": 100, "A": 50, "B": 20, "C": 1 }
      },
      "tiers": [
        {
          "id": "rule-1-tier-hot-a",
          "name": "热销A",
          "isDefault": false,
          "conditions": [{ "grade": "S", "operator": "gte", "count": 2 }],
          "coefficients": {
            "黑白": { "redLine": 3, "normal": 5, "peak": 8 },
            "彩色": { "redLine": 2, "normal": 4, "peak": 6 }
          }
        },
        {
          "id": "rule-1-tier-default",
          "name": "默认档",
          "isDefault": true,
          "conditions": [],
          "coefficients": { "...": "..." }
        }
      ]
    },
    {
      "id": "rule-default",
      "name": "默认模式",
      "isDefault": true,
      "factors": [],
      "grades": { "monthlyAvgCount": { "S": 120, "A": 90, "B": 30, "C": 1 } },
      "tiers": [{ "...": "..." }]
    }
  ]
}
```

要点：
- `grades` 的 key 集合 = 该模式**启用**的评分因子（key 存在即启用，没有单独开关字段）。
- `factors: []` + `isDefault: true` = 无条件命中，仅默认模式允许。
- 档位数组顺序即判定顺序；`isDefault: true` 的档必须在末位，每条模式必须且只有一个。
- 系数单位「周」，允许 0.5 步进、1 位小数。

## 6. 校验规则

`validateConfig(config)` → `{ ok, errors, warnings }`（[validate.js](/d:/Ghaniyy/Code/Demo/网布表格/kucunyujing1.1/src/stocking/validate.js)）

**errors（阻断保存）**
- 模式名字为空 / 重复
- 档位名为空 / 同一模式内重复
- 非默认档没有条件（永远不命中）
- 阈值未从 S 到 C 严格递减
- 系数缺失、为负、或违反 `红线 ≤ 正常 ≤ 峰值`
- 缺少默认模式 / 默认档

**warnings（提示不阻断）**
- 非默认模式的模式因子为空（不参与匹配）
- 模式未启用任何评分因子（全部记 Z）
- 某因子未配置任何阈值（该因子记 Z）
- 档条件数量超过已启用因子数（永不命中）
- 两条模式的因子区间可能重叠（静态区间相交检测 `detectRuleOverlap`）

交互约定：

- **删除模式需二次点击**：首次点击按钮变为「确认删除？」，3 秒内再点才真正删除，超时或切换模式自动复原（按钮固定宽度，避免抖动）。档位 / 因子 / 条件的删除不做确认，靠撤销兜底。
- **撤销 / 重做覆盖未保存的草稿**：改动前存 JSON 快照，连续输入（改名、阈值、系数）按 600ms 合并为一步，结构性操作（增删模式 / 档位 / 因子 / 条件）各自单独成步，栈深 50。
- 快捷键 `Ctrl+Z` 撤销、`Ctrl+Shift+Z` / `Ctrl+Y` 重做；焦点在输入框内时不拦截，交还浏览器的文本撤销。
- 点「确定」保存、点「重置」丢弃、点「恢复默认」之后都会清空历史（历史只描述未保存的改动）。
- 外部整体替换草稿时会递增 `draftVersion` 重挂编辑器，否则 `ElInputNumber` 会保留旧的输入态（撤销后数字框仍显示改过的值）。

- 命中分布延迟 250ms 重算，避免逐键全量评估 3 万行。
- 表格展示的是**已保存**配置的计算结果，草稿不影响表格。

## 11. 边界口径

| 情形 | 处理 |
|---|---|
| 周消耗 ≤ 0 | 模式缺省（灰），不再出现「预计库存 > 0 但三档都是 0」的紫色误判 |
| 色彩为空 / 非法 | 取不到系数 → 模式缺省 |
| 系数被清空 | `null` → 该行缺省 |
| 动销指标缺列/空值 | 该因子记 Z（不回退总表） |
| SKU 命中 0 条模式 | 归默认模式 |
| SKU 命中 ≥2 条模式 | 取靠前模式 + `ruleConflict` 标记 + 保存确认 |
| 模式改名 | 无影响：关联用 `ruleId`/`tierId`，不是名称 |
