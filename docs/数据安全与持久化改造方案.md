# 数据安全与持久化改造方案

> 适用对象：`/`（主面板）、`/sales`（销售表）、`/config`（配置信息）。
> 目标：把「公开演示站」改造成「公网可访问、但只有指定人能进、数据不落公开仓库」的内部系统。

## 1. 结论先说

| 问题 | 答案 |
| --- | --- |
| 现在能直接上生产吗？ | **不能**。仓库 public、站点公开、无鉴权、无后端、数据只在 localStorage。 |
| 一定要账号密码吗？ | **不一定要**。邮箱一次性验证码、企业 SSO（飞书/企微/微软/Google）、设备证书、VPN 都能做到「无密码」。 |
| 靠 robots.txt 防抓取够吗？ | **不够，且不算安全措施**。robots.txt 只是「请勿抓」的礼貌请求，AI 爬虫多数不遵守。真正有效的是**默认拒绝（未登录看不到内容）**。 |
| 公网服务器可以放吗？ | 可以。前提是**前置一层认证**，让未认证请求在到达应用前就被挡掉。 |

## 2. 防抓取的真相（重要）

搜索引擎抓取 = 请求 HTML → 执行 JS → 抓 DOM。所以：

- `robots.txt` / `<meta name="robots">` / `X-Robots-Tag` 只对**守规矩的**爬虫有效（Google、Bing、百度基本遵守）。
- 主流 AI 爬虫（GPTBot、ClaudeBot、Google-Extended、CCBot、PerplexityBot、Bytespider、Amazonbot）**多家已声明不遵守 robots.txt**，或被明确排除在「遵守」范围外。
- 结论：**noindex 只是锦上添花，鉴权才是命门**。
- 另有一条更现实的泄露路径：**GitHub 公开仓库本身就会被 AI 训练抓取**。代码里 `import` 的 JSON 会被打包进公开 JS，等于把真实业务数据直接发布出去。仓库必须转私有。

## 3. 访问控制方式对比（谁能进）

| 方式 | 用户操作 | 是否需要密码 | 安全强度 | 说明 |
| --- | --- | --- | --- | --- |
| **邮箱一次性验证码 / Magic Link** | 输邮箱 → 收验证码/点链接 → 进 | 否 | 高 | 推荐首选。Cloudflare Access、Authelia、Supabase 均内置 |
| **企业 SSO 扫码**（飞书/企微/钉钉/微软/Google） | 扫一下 | 否（复用已有账号） | 高 | 国内体验最好，账号离职即失效 |
| **设备证书 mTLS** | 装一次证书，之后无感 | 否 | 很高 | 只给固定几台办公电脑用 |
| **VPN / Tailscale** | 装客户端并授权设备 | 否 | 很高 | 完全不开公网端口 |
| **IP 白名单** | 无感 | 否 | 中高 | 出口 IP 固定才可行，手机 4G 会进不来 |
| **长随机路径** | 无感 | 否 | 低 | 链接一转发就失守，**不可单独使用** |
| **用户名 + 密码**（自建登录 / Basic Auth） | 记密码、易共享 | 是 | 中 | 最传统的做法，也是最容易「密码贴在聊天群里」的做法 |

**推荐组合：自有公网服务器 + 域名 + Cloudflare（DNS 代理）+ Zero Trust Access（邮箱 OTP 或飞书 SSO）**。不需要自建账号体系。

### 3.1 方案 A（推荐）：自有 VPS + Cloudflare Access

1. 域名托管到 Cloudflare，DNS 记录开橙云代理。
2. Zero Trust → Access → Applications → Self-hosted，绑定 `erp.example.com`。
3. Policy 设为 **Allow + Emails in [指定邮箱列表]**（或 `域名 = @yourcompany.com`）。
4. Identity provider 选 **One-time PIN**（邮件验证码）或飞书/微软 SSO。
5. Session duration 设 7 天（不用天天登录）。
6. 源站防火墙只放 Cloudflare IP 段，开启 Authenticated Origin Pulls，防止绕过。

效果：未认证访问在边缘就被 302 到登录页，**爬虫拿到的只有登录页，拿不到任何业务页面**。

### 3.2 方案 B：国内 VPS + Nginx + Authelia（不依赖 Cloudflare）

适用：服务器在国内、需备案、或不想走境外节点。

- `Nginx` 反向代理 + `Authelia`（默认 deny，`one_factor` 走邮箱 OTP / TOTP，或对接飞书/企微 OAuth）。
- 或 `oauth2-proxy` + 企业微信/飞书扫码：用户**从不需要密码**。
- 静态产物放 `/var/www/inventory`，API 服务只监听 `127.0.0.1`。

### 3.3 方案 C：Tailscale / WireGuard（最省事、最安全）

- 不开公网 80/443，只把服务器加入私有网络。
- 指定电脑装客户端并授权设备即可访问，**没有任何登录表单**。
- 适合使用者只有 5~10 台固定电脑的场景；缺点是手机临时查看不方便。

## 4. 防抓取配置清单（叠加在鉴权之上）

在仓库/服务端补齐以下内容（当前 `public/` 下**没有 robots.txt**，`index.html` **没有 noindex**）：

```text
# public/robots.txt
User-agent: *
Disallow: /
```

```html
<!-- index.html -->
<meta name="robots" content="noindex, nofollow, noarchive, noimageindex">
```

```nginx
# Nginx
add_header X-Robots-Tag "noindex, nofollow, noarchive, noimageindex" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "no-referrer" always;
```

Cloudflare 侧：
- Security → Bots → 开启 **Block AI bots**（一键拦截已知 AI 爬虫）。
- 或用 WAF 规则拦截 UA 含 `GPTBot|ClaudeBot|CCBot|Bytespider|PerplexityBot` 的请求。
- 注意：这些规则对**已通过 Access 的浏览器**无影响。

## 5. 数据持久化设计

### 5.1 现状

| 数据 | 现在存哪 | 问题 |
| --- | --- | --- |
| 库存 / 销售表导入行 | 只在内存（`src/stores/inventory.js`） | 刷新即丢 |
| 配置方案 | `src/stocking/config.json` + localStorage | 编译进包 → 公开；缓存不可靠 |
| 手动策略 SKU | `src/stocking/manualSkus.json` + localStorage | 同上 |
| 采购设置 / 下单数据 | `src/purchase/settings.json` + localStorage | 同上，且**已含真实厂名与人名** |

localStorage 不是持久化：单浏览器、不共享、不加密、清缓存即丢、同机任何人可读。

### 5.2 目标结构

```text
浏览器 (Vue SPA)
   │  HTTPS + 会话 Cookie
   ▼
认证层（Cloudflare Access / Authelia / oauth2-proxy）
   │  注入已验证身份（email）
   ▼
API 服务（Fastify / Express / Workers）
   │  校验身份 → 业务校验 → 写库 → 写审计
   ▼
数据库（PostgreSQL 或 SQLite）
   └─ 每日备份 → 异构私有对象存储（保留 30 天）
```

建议表结构：

| 表 | 关键字段 |
| --- | --- |
| `inventory_rows` | `panel_key`、`sku_id`（唯一标识，与 `src/utils/inventoryImport.js` 对齐）、`payload jsonb`、`updated_at`、`deleted_at` |
| `sales_rows` | `sku_id`、`month`、`count`、`weight`、`orders` |
| `sku_plans` | `sku_id`、`planned_qty`、`updated_by`、`updated_at` |
| `stocking_profiles` | `profile_id`、`config jsonb`、`active`、`updated_at` |
| `manual_skus` | `sku_id`、`mode_id`、`coefficients jsonb` |
| `purchase_settings` / `purchase_orders` | 原有结构原样入表 |
| `audit_log` | `actor`、`action`、`target`、`before`、`after`、`at` |

### 5.3 安全要求

- **传输**：强制 HTTPS、HSTS；HTTP 一律 301。
- **会话**：`httpOnly + Secure + SameSite=Lax` Cookie，Token 不放 localStorage。
- **授权**：写操作校验 Access JWT（Cloudflare 会带 `Cf-Access-Jwt-Assertion`，需验签），并校验邮箱在允许名单内。
- **敏感字段**：客户名、价格用 AES-GCM 字段级加密，主密钥放 Secret Manager / 服务器环境变量，**不入库、不入包、不入 git**。
- **数据库**：只监听回环/私网，不对公网开放端口。
- **日志**：不打印客户名、价格、完整请求体；错误信息不回显 SQL。
- **备份**：每日 `pg_dump` / SQLite 快照 → 异地私有桶，保留 30 天，每季度演练一次恢复。
- **审计**：每次「需安排」「实际计划」「下单」的写入都留 actor + before/after。
- **离职/调岗**：在 Access 策略里删邮箱即立刻失效（这是相对自建账号最大的优势）。

## 6. 与现有代码的改造点

改动面很小：持久化已收敛在 4 个模块，替换读写实现即可，视图层不用动。

| 文件 | 现在 | 改为 |
| --- | --- | --- |
| `src/stocking/persistence.js` | DEV 写文件 / 生产写 localStorage | `GET/PUT /api/stocking-profiles` |
| `src/stocking/manual.js` | 同上 | `GET/PUT /api/manual-skus` |
| `src/purchase/persistence.js` | 同上 | `GET/PUT /api/purchase/settings`、`/api/purchase/orders` |
| `src/stores/inventory.js` | 仅内存 | 进入面板时 `GET /api/inventory`，导入/编辑后 `PUT` |
| `src/stocking/config.json`、`src/purchase/settings.json` | 被 `import` 进包 → **公开** | 只保留空白/演示默认值，真实值从 API 拉 |

新增：


## 7. 分阶段落地

| 阶段 | 内容 | 预估 |
| --- | --- | --- |
| **P0 止损** | 脱敏 `src/purchase/settings.json`、`src/stocking/config.json`（真实厂名/人名换占位）；仓库转 Private；停用公开 Pages；补 `robots.txt` + `noindex`；`git filter-repo` 清理历史中的敏感提交 | 0.5~1 天 |
| **P1 上私有门** | 服务器 + 域名 + HTTPS + 前置认证（Cloudflare Access 或 Authelia）；先只部署前端，数据仍走 localStorage，但**站点已不公开** | 1~2 天 |
| **P2 数据落库** | 后端 API + 数据库；替换 4 个持久化模块；导入数据落库；配置/设置从 API 加载 | 1~2 周 |
| **P3 加固** | 字段加密、审计日志、每日备份 + 恢复演练、密钥轮换、依赖扫描 | 3~5 天 |

## 8. 验收清单

- [ ] 仓库已转 Private，且公开 Pages 站点已下线
- [ ] `git log -S "真实厂名"` 无结果（历史已清理）
- [ ] 构建产物 `dist/assets/*.js` 中搜不到任何真实厂名、人名、客户名、价格
- [ ] 未登录直接访问域名 → 只看到登录页，抓不到 HTML 内容
- [ ] `curl -s https://域名/ | head` 返回登录页而非应用
- [ ] 未授权的邮箱无法登录（策略测试）
- [ ] 断网重连后数据仍在；换一台电脑登录能看到同一份数据
- [ ] 删除浏览器缓存后数据不丢（证明已不在 localStorage）
- [ ] 每天备份成功，且完成过一次「从备份恢复」演练
- [ ] 审计日志能查到「谁在什么时候改了多少需安排量」
- [ ] 本地 `npm run dev` 不需要任何登录即可完整自测
- [ ] 直连源站 IP 访问失败（`curl --resolve 域名:443:<源站IP> https://域名/`）

## 9. 明确不做的事

- 不把真实数据写进任何 `import` 的 JSON（会进公开 JS 包）。
- 不用「长随机路径」当访问控制。
- 不继续在 GitHub Pages 上承载真实数据（Pages 无法加鉴权）。
- 不把 token / 密码放 localStorage。
- 不把数据库端口暴露到公网。
- 不为自动化测试在认证层开 bypass 规则（用 Service Token 代替）。

## 10. 开发与自动化测试（Agent / AI 怎么验证）

### 10.1 关键原则：认证做在应用之外

| 做法 | 开发时 | 安全强度 |
| --- | --- | --- |
| **应用内登录**（Vue 路由守卫 + token） | 开发要启动后端、造账号、处理 401，每次改完都得登录一次 | 低：bundle 是公开的，路由守卫只是「藏 UI」，不是安全边界 |
| **应用外认证**（Cloudflare Access / Nginx + Authelia） | `npm run dev` 走 `localhost:5173`，**完全不经过认证层**，零额外步骤 | 高：未认证请求在边缘就被拦掉 |

这就是选「前置认证」而不是「写登录页」的最重要原因：**开发体验不受影响，安全性反而更高**。

### 10.2 本地 / CI

| 场景 | 地址 | 认证 | 数据 |
| --- | --- | --- | --- |
| 本地开发 `npm run dev` | `localhost:5173` | 无 | 本地文件 / 本地 SQLite |
| 自动化测试（Playwright / Vitest） | `localhost` | 无 | 测试 fixture，每次重建 |
| 本地预览 `npm run preview` | `localhost:4173` | 无 | 本地 |

硬规则：**开发环境与测试环境永不连生产数据库**。这样「本地不需要登录」完全不是风险——本地本来就没有真实数据。

对 Agent 而言：改完代码直接 `npm run dev` + 浏览器验证，行为和现在完全一致，不需要任何登录脚本。

### 10.3 需要验证真实环境时，用机器身份，不要开后门

1. **Cloudflare Access Service Token**（推荐）
   - Zero Trust → Access → Service Auth 新建一个 token。
   - 自动化请求带上：
     ```http
     CF-Access-Client-Id: xxxx.access
     CF-Access-Client-Secret: yyyy
     ```
   - 凭证写 `.env.local`（已在 `.gitignore`），Playwright 可用 `extraHTTPHeaders` 注入，`curl` 直接加 `-H`。
   - 好处：**可随时吊销、可限时**，比在策略里开 `Bypass` 安全得多。
2. **专用测试账号**：把一个只读邮箱加入 Allow 名单。
3. **只读策略**：生产环境对自动化只放行 GET，写操作留人工执行。

### 10.4 唯一真实的「绕过」风险

Access / Authelia 由边缘执行，但如果**源站 IP 能被直连**，整个认证就被绕过（攻击者绑 hosts 或直接访问 IP）。必须同时做到：

- 源站防火墙只放行 Cloudflare IP 段（或只监听内网，由前置网关反代）；
- 开启 Authenticated Origin Pulls（mTLS），源站只接受来自 Cloudflare 的客户端证书；
- 数据库端口不对公网开放（只监听 `127.0.0.1` 或私网）。

验收：`curl --resolve 你的域名:443:<源站IP> https://你的域名/` 必须失败。

### 10.5 如果仍然想做应用内登录

那必须满足：

- 后端**每个接口**独立验签（不能只靠前端路由守卫）；
- 开发态用 `import.meta.env.DEV` 跳过登录页，且该分支在生产构建中被 tree-shake 掉；
- 接受「每次改完要登录一次」的开发成本（可用长会话 Cookie 缓解）。

不推荐：多写一套容易被绕过的代码，安全强度还低于前置认证。
