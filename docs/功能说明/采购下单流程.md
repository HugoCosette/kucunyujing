# 采购下单流程（功能说明）

> 一句话：**主面板把「需安排」定准（公斤、到个位，采纳即锁定）→ 该锁定数传到采购下单页，每张分订单可独立选择按缸或按公斤，再按染厂拆单 → 点「确认下单」后成为「订单」，主面板「备货」列的「累积下单」随之增加、该 SKU 进入「已下单」→ 逐单登记到货（或导入里出现生产入库）把在途清掉 → 该 SKU 转进「已到仓」、回到普通 SKU → 撤销可回退需安排 → 导出对账。**
> 原则：**缸只在「下单」环节出现**，不用来改备货建议值；订单日常追加、改单留痕、撤销作废，历史页另提供显式物理删除（可删整批或单张分订单，并级联删除到货 / 改单明细）；订单以「唯一标识」为键，重新导入不丢；**需安排与预警的判定规则一字不改**，只是「预计库存」里多算了「累积下单」的量。

## 3. 全流程分步

### 3.1 生成「需安排」（主面板，公斤、精准到个位）

| 方式 | 入口 | 数值来源 | 写入口径 |
| --- | --- | --- | --- |
| 单行填写 | 表格「需安排」列输入框 → `采纳` | 已填草稿；没填就直接用占位建议值 | **覆盖**该行，然后跳到 `/purchase` |
| SKU 弹窗填写 | 行内「详情」按钮 → 弹窗「需安排」动作条 → `采纳`（输入框里按 **Enter** 等价） | 已填数字 > 已保存的需安排 > 建议值 | **覆盖**该行，**不跳转**：弹窗原地转成「已采纳」锁定态，可继续看评分 / 图表或撤销 |
| 批量补货 | 勾选行（首列复选框 / 点整行 / 品名父行整组）→ 底部浮动条「确认补货」；**勾选即预填**（把 `getSuggestedPlanned()` 填进「需安排」输入框当草稿，取消勾选撤回未改动的预填）、**填数即勾选**（在「需安排」里填了正数自动勾上该行）；已采纳锁定的行不可勾选，订单提交后解锁 | 只传「需安排」里填着的数字，没数字的行跳过 | **覆盖**「需安排」，然后跳到 `/purchase`；默认选中这次写入的 SKU 里**下单列表最靠上**的那条（主面板按品名月均销量重排过，两边顺序不同，不能直接拿主面板第一条） |
| 紧急补货 | 工具栏「紧急补货 N」→ 填「新增计划」 | `ceil(正常库存 − 预计库存)` | 在现有需安排上**追加**（调用处先换算成绝对值） |

- 建议值口径（唯一一份在 [`utils/inventory.js`](../../src/utils/inventory.js) 的 `getSuggestedPlanned`）：`max(0, ceil(正常库存 − 理论库存 − 累积下单))`，即「补到绿色带中位（正常库存）」，**累积下单的部分视为即将到货先扣掉**，同一缺口不会被建议补两次。
- 有订单在履约（`累积下单 > 0`）时，需安排格**照常显示建议值**（已被扣掉累积下单的量），缺口没补够就可以继续下；进度看「在途库存」（还没进仓的量）与「下过单」。
- **订单货**（手动策略 `behavior: 'order'`）不给建议值，占位显示「按订单填写」，按客户报量人工填；它不参与预警与评分。
- 模式缺省 / 不参与备货的 SKU 建议值为 0，需人工决定。
- 这里的数字**一律是精准公斤**，不做缸取整；占位提示会写明「下单页会再按缸规则建议整缸数量」。

### 3.2 采纳「需安排」（唯一写入路径）

```
行内「采纳」 ──┐
弹窗「采纳」 ──┤
批量「确认补货」┼─→ writePlanned(plans)  ← 页面内的唯一写入函数
紧急「确认提交」┘        │
                         ├─ 写入 item.planned（绝对值，覆盖）
                         ├─ 记 plannedUndoHistory（旧值，供撤销）
                         └─ 清掉该行的需安排草稿与预览色
```

- 弹窗那条链路只多一层事件：`SkuDetailDialog` 收 `plannedEditable` / `plannedLocked` 两个 prop、抛 `adopt-planned` / `undo-planned` 两个事件，写入仍由页面完成（主面板要重建表格行，顺带把弹窗持有的行对象换成新行）。销售表页的弹窗写的是同一个 inventory store，撤销记录也共用 `store.plannedUndoHistory`，切回主面板即可看到。

- 数量优先级：**单个采纳**（`resolveSubmitPlanned`）是「需安排输入框里已填的正数草稿 > 建议值（`getSuggestedPlanned`）」——清空过数字、从没填过都按建议值兜底，只有建议值也是 0（不缺货 / 缺系数 / 订单货没填）时才提示先填数量；**底部「确认补货」只认勾选行「需安排」里填着的数字**（勾选会自动带出建议值），不再回头取建议值兜底，没数字的行跳过（提示「N 个没有数量已跳过」）。
- `writePlanned` 只接受 `planned > 0` 的行，返回真正写进去的行；批量补货写完提示「已写入需安排：N 个 SKU」并**直接跳到 `/purchase`**（带 `?sku=` 把第一个写进去的 SKU 选中）。
- 采纳后该行「需安排」被锁定（输入框禁用 + 锁图标），**同时不能再被勾选**（选择列常驻显示锁图标替换复选框、整行锁形光标、点整行无效；行内「采纳 / 撤销」「SKU 弹窗」「订单弹窗」仍可正常点击）——避免已采纳的行又被底部「确认补货」带一次；确认下单时需安排清零并解锁，之后可以重新修改、采纳下一批。点「撤销」则恢复原值。
- 主面板筛选条的「下单中」按这个锁定状态筛出已采纳、等待采购页确认下单的 SKU；「已下单」按在途筛（已确认下单、还没到仓），「已到仓」按「下过单但已全部到仓」筛。三个按钮可以与预警、关键词等筛选条件叠加；确认下单后锁定解除，SKU 离开「下单中」、进入「已下单」，货进仓（在途归零）后转进「已到仓」，回到普通 SKU 等下一次预警。
- **锁定 = 生效**：锁定的数字就是这个 SKU 传到下单页的「需安排」总数，也是「预计库存」里唯一被采信的计划量。
- **未锁的需安排只是草稿**（现有实现即 `plannedDrafts`）：显示在格子里、可编辑，但**不计入预计库存**。撤销订单后回补的数字就落在这一层，所以预警会退回到红色。
- **没有第二份清单**：`/purchase` 的下单列表直接由 `planned > 0` 派生（按唯一标识关联行），所以清空需安排 / 确认下单后该行自动从下单面板消失，不需要再同步一份 `purchaseList`。

### 3.3 主面板的采购执行层（下过单 一列 + 在途库存的行尾图标）

表头分组由 `TABLE_COLUMNS` 相邻同组自动合并。「备货」组（累积下单 / 待收 / 到货）连同可折叠的大表头已经**整组删掉**：进入滚动导入后，到仓事实由导入的出入库明细决定，「待收 / 到货」这两列只认手工登记，会和「在途库存 = 0、在仓库存已经涨了」自相矛盾。现在采购执行层只剩两处：

```
信息 · 商品 │ 入口：需安排 · 生产中 · 已安排 · 下过单 │ 出口：欠货 · 周销量 │ 库存(公斤)：周转入 · 在途库存 · …
```

| 位置 | 显示 | 取数（只来自订单，不来自导入） |
| --- | --- | --- |
| 入口组 · 下过单 | 该 SKU **累计下单公斤** | Σ `status = active` 的 `quantity` |
| 库存(公斤) · 在途库存的行尾图标 | 小文档图标，点开分订单明细（见 3.4） | 该 SKU 有未作废订单时出现；在途归零后转灰，表示「下过单、已全部到仓」 |

- **下过单只增不减**：货到仓、重新导入都不会清零，它是「这个品下过单」的留痕；**判断到没到仓不能看它**，要看「在途库存」（`在途 = max(0, max(下单累计, 排单累计) − 生产入库累计)`，到仓自动归零）。
- 想按状态筛用筛选条采购组：**已下单** = 下过单且在途 > 0；**已到仓** = 下过单且在途 = 0。
- 该 SKU 没有订单时「下过单」显示 `0`，行尾图标不出现（父行一律不出现）。

### 3.4 分订单明细弹窗（只读对账 + 补登记到货兜底）

视觉与 `docs/prototype` 的订单弹窗同源：细边框 3px 圆角的弹窗外壳 + 灰蓝标题条（品名 + 颜色 chip + 右端关闭按钮），宽度 `min(760px, 100vw - 32px)`，**高度跟着内容走**（`height: auto` + `max-height: 75vh`），内容超长时中间滚动、底部口径说明常驻。

| 区域 | 内容 |
| --- | --- |
| 列头（汇总） | 左「分订单」：`N 张 · 下单合计 X 公斤`；右「到仓对账」：`在仓 Z · 在途 Y 公斤`（在途归零标绿）——两个数都取自主面板那一行，即导入对账的结果 |
| 分订单行 | 每张一行：小序号 + 染厂 + 分单人员 + 右对齐下单时间（`月-日 时:分`）；下一行是 `下单 X 公斤`（按缸下的还带 `缸 N`）+ 有过补登记时多一个灰色 `补登 X`，最右是 `⋯` |
| `⋯` 菜单 | **改单**（改下单公斤，不能少于已补登量，写 `revisions` 留痕）/ **补登记到货**（导入没跟上时兜底扣在途）/ **撤销整单**（`status → cancelled`，公斤数回主面板需安排草稿层） |
| 底部说明 | 「到仓以导入的出入库明细为准（生产入库 → 在途归零、在仓增加）；导入还没跟上或来源单据没匹配上时，用 ⋯ → 补登记到货 先把在途扣掉」，有过补登记时补一句合计 |

- **为什么不再按单登记到货**：导入只有 SKU 级的生产入库总量，还原不出「每张分订单各自到了多少」；按单勾到货是手工时代的模型，跟滚动导入永远对不上。所以原来的两栏（左分订单 / 右到货记录 + 登记到货 + 撤回·恢复·删除）整块撤掉，到货只留 SKU 级的「补登记」兜底。
- **补登记到货**仍然写 `receipts`（`receivedQty` 由它求和派生），参与 `在途 = max(0, max(下单, 排单) − 生产入库 − 手工补登)`，所以补登能让在途提前归零；但它**不影响在仓库存**（在仓只认导入的库存结存表）。
- **撤销整单**：`status → cancelled`（行保留，不物理删除），该单未撤的到货记录一并作废；公斤数加回「需安排」，落在未锁的草稿层，于是预警退回「紧急补货」，需要重新采纳才算有效计划。有补登记记录的分订单撤销前必须二次确认。

### 3.5 预计库存与预警（本版口径）

```
在途     = max(0, max(下单累计, 排单累计) − 生产入库累计 − 手工补登累计)
在仓kg   = 库存结存数量 × 公斤系数
预计库存 = 在仓kg + 在途 + 需安排锁定值
理论库存 = 在仓kg + 在途
```

- 红线 / 正常 / 峰值 的判定逻辑一字不改，仍拿预计库存与三档比较。
- **手工补登只动在途、不动在仓**：补登后待收减少、在途减少，合计不变，所以补登记不会让预警跳色；导入出现生产入库后才真正转到在仓。
- 三个数各司其职、互不覆盖：**需安排 → 计划**、**下过单 → 订单留痕**、**在仓 / 在途 → 事实**。

> 这段上面的旧写法（「预计库存 = 在仓 + 在途 + 累积下单」、逐单登记到货）是**一次导入用很久**时代的口径；滚动导入后同一批货会同时出现在「累积下单」和「生产排单」里，那样算会翻倍。新口径就是本节这段公式，实现在 `calculateInventoryRow`（收到 `inTransitKg` 即生效）与 `src/purchase/inTransit.js`。

### 3.6 待下单列表（没有独立的「本次采购清单」）

- 主面板曾经有一个「本次采购清单」弹窗（顶部按钮 + 飞行动画 + `purchaseList` 状态），现已删除：**需安排就是清单**。
- `/purchase` 的下单列表 = `inventoryStore.inventoryItems` 里 `planned > 0` 的行（按唯一标识关联分订单），所以「哪些 SKU 要下、下多少」只有一处真相。
- 行从列表消失的唯一方式是把需安排清零：确认下单、下单页「撤销」（清草稿 + 需安排清零解锁）。

### 3.7 采购下单页（按染厂拆单 → 确认下单）

- 顶部**只留标题「采购下单」**，不再占一整行放总进度。
- 总进度收进左面板的标题行：`下单列表` → `9/9 单` → 进度条（**撑满整行剩余宽度**）。口径是 `已填分订单的 SKU 数 / 待下单 SKU 总数`（一个 SKU 算一单）：**填满 8 成 SKU 就是绿、不足是黄**（阈值 `FILL_LOW_RATIO` 与左列表「下单数量」的 80% 线共用），不再按公斤比例、也不再按"最差 SKU"汇总（超一缸的红色只在单 SKU 那条上出现）。公斤合计（`已下单 / 需安排`）与阈值说明在 hover 里（`progressTitle`）；未下单有几个看「未下单」筛选 chip。
- 左列表：面板头是「**下单列表**」+ 紧跟标题的单数进度（`9/9 单` + 撑满整行的条，见上），不再显示 `N / M` 计数。列是**品名 / 颜色 / 需安排 / 下单数量 / 操作**（左栏 460px，右侧明细相应收窄）。品名与颜色分列，颜色给足宽度（超长仍有 `title` 兜底），品名压灰、颜色用正文色；「需安排」「下单数量」两列表头与数字都**居中**。「下单数量」直接显示这一刻已填分订单的实际公斤数（＝本次分单合计，确认下单后该 SKU 就从列表移除，已确认量不会留在这里），颜色按下面同一套口径标出下够了没；末列「撤销」常驻在每个 SKU 行上，**点一次变成「确认撤销」、再点一次才执行**（不弹窗），点其他地方或别的行会取消待确认状态；右侧 ⋯ 菜单里的「撤销这个 SKU」仍是弹窗二次确认。二次确认后清空草稿并把需安排清零解锁，该行自然离开下单面板；支持关键词搜索与「未下单」筛选 chip（带未下单计数）。选中行随筛选自动回落到第一行；左右面板之间有一条从选中行指向明细的扇形连接件（位置随选中行 / 滚动 / 缩放重算，量不到时自动隐藏）；**手动切换 SKU 时先由左向右扫过选中行，再接续由左向右展开扇形连接件**（尊重减少动态效果设置）。树形分类在右侧标题旁。
- **下单数量 / 进度条 / 差额文字的颜色口径**（唯一实现 `src/purchase/fillTone.js`）：未下单灰 → **< 80% 黄** → **80% ~ 100% 绿** → **超出但还在一缸以内仍绿** → **超过一缸红**。「一缸以内」按该 SKU 的缸型判断（分订单里有 `kgPerVat` 快照就取最大那档，没有就退回缸规则建议的缸型），因为缸本来就要装满才省运费，多出半缸是正常取舍；没有缸型可容忍时（规则判定不下单 / 未绑定缸规则）只要超出就红。左列表数字悬停可查看颜色口径；右侧进度条悬停会分段展示进度、缸规则与颜色说明。
- 左列表底部（有草稿时才出现）：只有「**下单全部已填**」（＝把所有已填分订单的 SKU 一起提交；单数进度已经在标题行，不再重复写 `12/15`）。
- 右侧标题栏：`品名 · 颜色` + 树形分类 tag + ⋯ 菜单（**清空分订单** / **撤销这个 SKU**）—— 标题栏不放主操作。**「确认下单」在右下角**（底部操作条最右端，见下）。撤销清空该 SKU 已填的草稿，并把主面板该行的需安排清零、解除锁定（二次确认）；左列表每行末列的「撤销」是同一个动作，不用先选中再进菜单。
- 右侧编辑器（[`SkuOrderEditor.vue`](../../src/components/SkuOrderEditor.vue)，本页传 `variant="panel"`）：
  - 进度条：`已下单 A / 需安排 B 公斤` + 进度条，**不再写「还差 / 超出 / 与需安排一致」**——差额只用颜色表达（< 80% 黄、80% ~ 100% 绿、超一缸内绿、超过一缸红）。进度条尾部也不再挂建议灰字；悬停右侧进度条时按「下单进度 / 缸规则 / 颜色说明」分段展示完成比例、规则命中区间、建议下单量与颜色判定。
  - 表格列：`#` / 染厂 / 分单人员 / **下单方式** / 缸数 / **缸型（公斤）** / **下单量（公斤）** / 备注（缸号 / 交期）/ 删除。末列「删除」与主面板列表里的「撤销」同一套手感：**点一次变成红框红字的「确认删除」，再点一次才删掉这张分订单**（不弹窗），点别处 / 切 SKU / 行数变化自动取消。
  - 表格列宽固定为协调的像素宽度（合计约 1006px），窄屏或右侧面板空间不足时在表格容器内横向滚动，不压缩成参差不齐的列宽。
  - **下单方式按分订单独立保存**：选「按缸」时缸数为整数、缸型来自该 SKU 生效的缸规则（可手输自定义公斤数），下单量只读并按「缸数 × 缸型」计算；选「按公斤」时直接编辑下单量，缸数与缸型显示「—」，该行不计入缸数合计。同一 SKU 的多张分订单可以混用两种方式。
  - 按公斤下单量按整数公斤录入；显示与保存均取最近的整数公斤，不展示 `.00`。数量输入统一最多 6 位整数（≤ 999999 公斤，按缸数同样受限），键入或粘贴超出的位数就地截断；订单弹窗「改单」按同一条上限校验。分单表格（含列标题、数字与操作列）统一左对齐。
  - 切换下单方式后，对应的输入区域短暂闪亮提示：按缸高亮缸数与缸型，按公斤高亮下单量；提示色采用柔和浅金色，避免高亮过亮刺眼。
  - 分单表格下方空白区域居中显示填写提示：「按缸：填写缸数、选择缸型，下单量自动计算」「按公斤：直接填写下单量（公斤）」；提示文字不加粗、不加句号。
  - 「缸型（公斤）」候选由该 SKU 生效的缸规则生成（唯一实现 `vatQuantityOptions()`，在 `src/purchase/vat.js`）——列出各档的固定量 / 每缸公斤 / 缸型列表；当前建议缸型标「建议」。规则未配置缸型时也可在「按缸」下手输自定义缸型。
  - 切换到「按公斤」会将当前下单量取整为整数公斤；切换到「按缸」会使用当前或建议缸型，优先保留可整缸换算的数量，非整缸时取最近的整数缸数后重算公斤数。新建分订单默认沿用上一行的下单方式；首张自动建议单默认按缸。
  - 底部操作条（固定在面板底部）：**只有右下角的「确认下单」主按钮**（没填分订单时置灰，位置不跳）。原来左侧那串 `合计 N 张` / 合计缸数 / 合计公斤已删掉 —— 张数看表格行数、缸数与公斤看每行的缸数列和上方进度条；这里也不再写差额文字。
  - **进面板即带一张建议单**：选中某个 SKU（`/purchase` 左列表，含从主面板跳转自动选中的那条）时，若该 SKU 还没有分订单，编辑器会自动按缸规则对需安排量带出一张分订单（＝替人点了一次「＋ 添加分订单」）：公斤与缸数按缸规则换算（如 433 → 2 缸 × 240 = 480 公斤），染厂 / 分单人员取下拉第一项。同一 SKU 在一次会话里只自动带一次，删掉后不会自己长回来：`deletedSkus`（模块级，弹窗关了再开、切走再回来都记得）记下「分订单从有变一张不剩」的 SKU —— 末尾的「删除」删到空、⋯ 菜单「清空分订单」清到空都算，所以删除始终是**两次点击**（一次确认），不会删完立刻又长出一张新单；重新有分订单（手动添加 / 批量填单 / 重新下单）后解除记忆；只有人点选的行才自动带，筛选导致的自动回落不预填（否则一开「未下单」筛选就会把回落到的每一行都预填、再把它们逐条筛掉，连锁填满整张清单）。
  - 「＋ 添加分订单」再加一张时同样带默认值，但按「还差多少需安排（需安排 − 已下单）」换算，染厂 / 人员沿用上一张；需安排已下满时新行从 0 公斤起填（不再跟一行说明文字）。
  - 「清空分订单」需二次确认。
- 主面板不再有「去下单」弹窗：采纳 / 确认补货直接进本页，分订单编辑器只在这里出现。
- **编辑即草稿**：下单页填的行先存 `drafts[skuId]`（自动保存，防抖 400ms），主面板完全感知不到，需求表数字一格都不动。
- **确认下单**：单个 SKU 右下角的「确认下单」，或左列表底部「下单全部已填」（把所有已填分订单的 SKU 一起提交，带二次确认）。确认时按染厂各生成一张订单（同一批共用 `batchId`），写 `submittedAt`、`status = active`，并清空该 SKU 的草稿。
- 确认后主面板该 SKU：**需安排 → 0、锁解除、格子回到空白**（占位建议值照常出现，已扣掉这批累积下单），「累积下单」+= 本批公斤。
- 下单页「撤销」（**确认前**，左列表每行的「撤销」按钮 / 右侧标题栏 ⋯ 菜单）：清空该 SKU 草稿，主面板需安排清零并解锁 —— 等同「这个 SKU 先不下了」。
- 部分下单（确认量 < 需安排）时同样清零解锁；没下够的部分由预警提示重新补货，不会自动留在需安排里。

### 3.8 订单模型与落盘

| 项目 | 说明 |
| --- | --- |
| 结构 | `{ version: 2, updatedAt, drafts: { [skuId]: Entry[] }, orders: Order[] }` |
| 草稿 | `drafts[skuId]`：下单页正在填的行，运行时可留空白行，**不算已下单** |
| 订单 | `orders[]` 扁平一行 = 一张分订单（SKU × 染厂）；日常追加、改单留痕，历史页可物理删除单张分订单或整批 |
| 订单字段 | `{ id, batchId, skuId, product, color, factoryId, factoryName, assignee, quantityMode, quantity, vatCount, kgPerVat, note, status, submittedAt, updatedAt, month, receivedQty, receipts[], revisions[], cancelledAt }` |
| 下单方式 | `quantityMode` 为 `vat`（按缸）或 `kg`（按公斤）；旧草稿 / 订单缺少该字段时，有完整缸数与缸型快照的按缸归类，其余按公斤兼容 |
| status | `active` / `cancelled`；到货进度由 `receivedQty` 与 `quantity` 比较派生，不单设状态 |
| 到货 | `receipts: [{ at, qty, by }]`，`receivedQty = Σ receipts.qty`；撤销到货 = 撤掉最后一条 |
| 修订 | 允许修改已提交订单，每次保存追加一条 `revisions[]`（时间 / 操作人 / 改前 / 改后） |
| 迁移 | v1 的 `{ orders: { [skuId]: Entry[] } }` 逐条迁成 `active` 订单，`submittedAt` 取文件 `updatedAt`、`batchId = legacy-{updatedAt}` |
| 写入 | 统一走 `purchaseStore` → 防抖 400ms 落盘，`pagehide` 时 flush |
| 索引 | store 维护 `bySku` 聚合（累积下单 / 到货 / 待收 / 张数 / 单据），主面板按 `skuId` O(1) 取值，**不要逐行扫全表** |

### 3.9 导出与对账（`/purchase` 工具条「导出待下单」+ 页头「导出订单」）

文件名 `待下单清单-{时间戳}.xlsx`，两个工作表：

| 工作表 | 列 |
| --- | --- |
| 待下单清单 | 品名、颜色、树形分类、需安排、**缸数**、**每缸公斤**、建议下单、累积下单、到货、待收、分单数量 |
| 分单明细（有分单时才出现） | 品名、颜色、树形分类、染厂、分单人员、下单方式、缸数、缸型（公斤）、下单量（公斤）、到货、待收、备注 |

- 「缸数 / 每缸公斤 / 建议下单」由导出行现算（需安排 × 品名绑定的缸规则）；分单明细中的 `vatCount` / `kgPerVat` 是按缸方式的快照，按公斤分单则导出方式与实际下单量。
- 界面上的清单**不显示**缸数列；缸数建议只出现在下单环节与导出文件里。导出走 `src/utils/xlsxWrite.js` 的 `saveWorkbook`，两个工作表一次写出。
- 采购页页头「导出订单」取已持久化的 `orders[]`，与左侧待下单列表、未确认草稿无关：确认后 SKU 从列表移走、甚至列表空了，那个批次仍能导出。三档入口：**本次确认批次**（本次会话最后一次确认生成的同一 `batchId`，含作废行）/ **今日已确认**（本地日期当天的有效单）/ **自定义日期范围**（两个原生日期输入，含起止两天，可选有效单 / 已作废 / 全部状态）。
- 「本次」= 最后一次点「确认下单 / 下单全部已填」这一次操作实际创建的分订单，不含此前或之后确认的单；逐 SKU 分开确认各成一批，同一分钟也不会合并。确认成功的 toast 会提示去「导出订单 → 本次确认批次」。
- 这两档导出的工作簿结构与下单历史一致（批次汇总 + 分订单明细），共用 `src/purchase/historyExport.js`。

### 3.10 下单历史子面板（`/purchase/history`）

「采购下单」页内两个子面板：**下单面板**（`/purchase`，拆单 + 确认下单）与**下单历史**（`/purchase/history`）。标签页在页头下方（`.purchase-tabs`），两者共用 `PurchaseOrderView.vue`，按 `route.name` 决定渲染哪块；切到历史时页头的统计条自动隐藏。

下单历史一站式查「我下过的所有单」，不再需要逐张 SKU 打开订单弹窗。数据全靠 `orders[]` 派生（`src/purchase/history.js`）；批次带可删除整批，分订单行可单独删除。删除是永久操作，确认后从 `orders[]` 移除订单并级联清除其 `receipts[]` / `revisions[]`，下单量、到货量、待收与历史汇总随之重算；批次删除按完整 `batchId` 执行，不受当前搜索 / 状态筛选影响。

界面形制照标准订单列表（Polaris IndexTable / Ant Design Table 可展开行 / Stripe 发票列表那一类）：

- **只有一套表头**，批次不再自带第二张表；批次是一条**与子行同列的分组带**，本级合计正好落在「下单 / 已到货 / 待收 / 进度 / 状态」各列下面，不用再读一句「下单 X 已到 Y」；
- **子行缩进 24px + 左侧细引导线**，白色底；分组带浅灰底 + 上边框，形成「一块一块」的节奏；
- 数字一律**左对齐**、千分位、`tabular-nums`；**为 0 的数字全部降灰**，只有真正需要关注的数值才是深色；
- 进度**只显示百分比**，不画进度条（作废行显示「—」）；
- 状态用「圆点 + 文字」而不是彩色块；底部一行**合计**（批次 / 分订单 / 下单 / 已到 / 待收）；
- 默认只展开最近一个批次，其余折叠，避免一屏几十行。

| 层级 | 内容 |
| --- | --- |
| 批次带（= 一次「确认下单」的 `batchId`） | 批次号 `PO-YYYYMMDD-NN`（按本地确认日期顺排，与流水一致、换筛选不变）、确认时间、SKU 数、分订单数、作废数、下单 / 已到货 / 待收合计、进度、状态（已收齐 / 部分到货 / 未到货 / 部分作废 / 已作废）、到货笔数与改单次数 |
| 分订单行（展开批次） | 品名、颜色（各占一列，不显示唯一标识）、染厂、分单人员、下单方式 / 缸型（按公斤或 `N 缸 × 每缸公斤`）、下单 / 已到货 / 待收、进度、状态、到货笔数（含撤回笔数）与改单次数、备注 |

- **筛选**：关键词（批次号 / 品名 / 颜色 / 唯一标识 / 染厂 / 人员 / 备注）、日期维度（全部日期 / 按月 / 按日 / 自定义范围）、状态（默认「有效单」，作废单要切到「全部状态 / 已作废」才显示）；筛选后批次的合计会跟着重算，界面上的数字永远等于看到的行。
- **日期与导出**：日期一律按本地确认日期解释（与「确认时间」列同一时区），自定义范围含起止两天；只填开始或结束一头时按单边过滤。导出就是当前日期 / 关键词 / 状态筛选后的批次与分订单，同一批次只有范围内命中的分单会被写出。
- **作废不进账**：`cancelled` 的分订单留在列表里灰显，但不计入下单 / 已到货 / 待收的合计；作废数只落在批次分组带的「作废 N」与行状态上，工具栏不再另挂一条汇总文字。
- **删除与需安排**：删除有效单后，该单从 SKU 有效订单汇总中移除，普通备货 SKU 的「需安排」建议按理论库存与剩余有效下单量重新计算，不把删除单的缸规取整量写回草稿；订单货仍无自动建议值。删除已作废单不再回补需安排，避免重复回补。删除单上的到货记录会一并移除，但导入的在仓库存不改；到货 / 改单信息会在确认框中提示。
- 批次号按当天现存批次顺排，删除批次后，同日剩余批次号可能重新顺排。
- **导出**：`下单历史-{日期范围}-{时间戳}.xlsx`（全部日期时省略范围段），两张表「批次汇总」「分订单明细」，导出的是当前筛选结果。
- 批次的 `submittedAt` 代表一次成功的确认下单操作；`batchId` 是“本次批次”边界。同一分钟的不同确认不会合并。
- 到货 / 改单 / 作废 / 恢复作废 / 登记到货仍在主面板订单弹窗中操作；历史页新增的物理删除走 store 写入口。

### 3.11 在途对账（滚动导入口径，已接入）

> 现状（2026-11-25）：清洗侧的到仓信号（总表 `生产入库` / `退货入库`）、口径模块
> [`src/purchase/inTransit.js`](../../src/purchase/inTransit.js)、主面板三列与基线持久化都已接入；
> 用 [`tools/cleaning/simulate-rolling.mjs`](../../tools/cleaning/simulate-rolling.mjs) 做过 1000 SKU × 7 天回放。
> 可直接导入 [docs/测试数据/滚动导入演示](../../测试数据/滚动导入演示/README.md) 按天体验。

每个 SKU 有三个**从切换日起算**的累计量（公斤）：

| 符号 | 含义 | 来源 |
| --- | --- | --- |
| `o` | 下单累计 | 本地订单流水，只算 `status = active` |
| `s` | 排单累计 | 生产排单「进仓重量」 |
| `r` | 生产入库累计 | 总表「生产入库」列（出入库明细里 `来源单据` 为生产 / 加工入库的 `入库数量`） |

```
在途     = max(0, max(o, s) − r)
生产中   = min(max(0, s − r), 在途)
已安排   = 在途 − 生产中
理论库存 = 在仓 + 在途
预计库存 = 理论库存 + 需安排
建议需安排 = max(0, ceil(正常库存 − 在仓 − 在途))
```

同一批 500 公斤在四个桶之间迁移，**预计库存全程不变**：

| 时点 | 在仓 | 需安排 | 已安排 | 生产中 | 在途 | 预计库存 |
| --- | --- | --- | --- | --- | --- | --- |
| D1 导入后（预警建议 500） | 1000 | 0 | 0 | 0 | 0 | 1000 |
| D1 采纳并下单 500 | 1000 | 0 | **500** | 0 | 500 | 1500 |
| D2 导入（排单出现 500） | 1000 | 0 | **0** | **500** | 500 | 1500 |
| D3 导入（生产入库 500） | **1500** | 0 | 0 | 0 | **0** | 1500 |

边界（`o / s / r` 都是公斤）：

| 场景 | o | s | r | 在途 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 部分到货 | 480 | 480 | 240 | 240 | 生产中 240，已安排 0 |
| 超产 | 500 | 600 | 0 | 600 | 多出的 100 也是要进仓的货 |
| 排单漏记、直接入库 | 500 | 0 | 500 | 0 | `max(o, s)` 兜住 |
| 退货入库 100 | 0 | 0 | 0 | 0 | 只让在仓 +100，不动在途 |
| 提前备货（非本系统下单） | 0 | 200 | 0 | 200 | 生产中 200 |

为什么这样定：

- **取 `max(o, s)` 而不是 `o + s`**：下单和排单是同一批货的两个视角，相加就是 3.5 那个翻倍问题。
- **减 `r` 而不是等排单消失**：排单导出是累计流水（实测 564 行里 558 行早于导出日，且没有完工状态列），只能靠生产入库证明货真的进仓了。
- **理论库存也用对账后的在途**，不再用排单原始累计：排单只增不减，D3 入库 500 之后那行还留在表里，
  `在仓 1500 + 排单 500 = 2000` 会把已经到仓的货再算一遍；改成 `在仓 + 在途` 后 理论库存 = 预计库存 − 需安排，三个数一眼能对上。
- **退货不入 `r`**：退货只让在仓增加；如果拿它冲抵在途，一张还在做的采购单会被「凭空到货」冲掉。

数据契约（必须守住，否则口径失效）：

1. 排单是**累计流水**，已完成的行不能从导出里删。若将来改成「只导未完成」，把 `scheduleMode` 切成 `pending`，生产中直接取 `s`。
2. 生产入库必须逐行写 `入库数量` + `来源单据`，并能区分生产入库 / 加工入库与销售退货入库。
3. 切换日基线（每 SKU 的 `s` / `r` 初值）必须落盘；导入侧减基线、订单侧只算切换日之后的单，否则历史产量会把在途撑爆。

接入位置（2026-11-25 已完成）：

1. `applySourceImport` 在第一次导入时创建基线并落盘（IndexedDB 文档 `inTransitBaseline`），之后每次导入只算增量；
2. `stores/inventory.js` 提供 `inTransitIndex` / `inTransitOf(skuId)`，主面板与 SKU 弹窗都从这里取，`calculateInventoryRow()` 据此切到新口径；
3. 主面板「入口」组新增 **已安排**，「生产中」显示净在产，「在途库存」显示对账后的在途；
4. 到货登记仍可用（计入到仓累计），生产入库上线后建议只依赖导入；
5. 设置 → 数据 → 本机数据存储里有 **「重置在途基线」**，换测试数据或口径跑偏时用它重新起算。

**上线前置条件**（2026-11-26 用真实导出核对过）：

1. **到仓信号必须存在**：2026-10-21 的明细里入库 9,447 行全是销售退货（`销售退货单` / `销售退货入库`），`生产入库` 合计 **0**。
   没有它，`在途 = max(o, s) − r` 只增不减 —— 排单上多少就永久挂在途多少，预警会慢慢失效（预计库存虚高 → 永不触发补货）。
   两条路：① 业务出「生产入库」单据，`来源单据` 命中 `/生产入库|加工入库|生产进仓|加工进仓/`（写成「成品入库」之类要扩这个正则，一行）；
   ② 系统内有单的 SKU 每天在订单弹窗登记「到货」（计入 `r`）—— 但排单里**没在本系统下过单**的产量（提前备货）冲不掉，只能靠 ①。
2. **先「重置在途基线」再导真实表**：基线只在第一次导入时建，建错了（比如先导了演示数据）就按错的初值一直算增量。
3. **排单保持累计流水**：实测 569 行进仓日期全部早于导出日、没有完工状态列；若将来改成「只导未完成」，要同时把 `scheduleMode` 切成 `pending`，否则在途会突然清零。
4. 实测明细表末尾有一行**合计行**（品名 / 颜色为空，入库数量 2,117,032），清洗按「无唯一标识」丢弃，不影响结果，但说明表里另有非生产 / 非退货的调拨或期初入库，需要业务确认口径。

## 4. 缸规则（只在下单环节生效）

### 4.1 数据模型（`src/purchase/settings.json`，设置版本 v3）

```jsonc
{
  "vatRules": [
    {
      "id": "vr-standard",
      "name": "标准大货补单",
      "bandKey": "planned",              // planned | skuMonthlyAvg | spuMonthlyAvg
      "remainder": "nearest",            // nearest | floor | ceil
      "remainderThreshold": 0.5,         // nearest：余量 ≥ 50% 一缸 → 补一缸
      "minVats": 1,                      // 需求 > 0 时至少几缸
      "bands": [                         // 从低到高，最后一档必须无上限；一行一段
        { "upTo": 120,  "action": "fixed",  "value": 80,  "sizes": [] },
        { "upTo": 200,  "action": "fixed",  "value": 160, "sizes": [] },
        { "upTo": null, "action": "ladder", "value": 240, "sizes": [240] }
      ]
    },
    {
      "id": "vr-small",
      "name": "小批量补单",
      "bandKey": "planned",
      "remainder": "nearest",
      "remainderThreshold": 0.5,
      "minVats": 1,
      "bands": [
        { "upTo": 50,   "action": "skip",   "value": 0 },
        { "upTo": null, "action": "ladder", "value": 60, "sizes": [60] }
      ]
    }
  ],
  "defaultVatRuleId": "vr-standard",     // 未绑定的品名用它
  "spuVatRules": { "品名A": "vr-small" }, // 品名（SPU）绑定，SKU 全部沿用
  "skuVatRules": {}                      // 例外：单个 SKU 覆盖；"__none__" = 不取整
}
```

- `sizes` 是**可用缸型**（公斤，归一化时升序去重，最多 8 种），只有 `ladder` 动作使用；其它动作归一化后是空数组。
- 一个 SKU 的缸型来自它命中的档：`ladder` 档自带一组缸型，`vat` / `round` 档等价于「只有一种缸型」。
- 编辑弹窗里「一行 = 一段」：除最后一行外都存成 `fixed`（补到那个公斤数），最后一行存成**单缸型**的 `ladder`（`sizes` 只有一个值，超过它才好按它补多缸）。所以老的多缸型 `ladder` 规则（80 / 160 / 240）打开时会被摊成 `0–120 / 121–200 / 201–不限` 三行，保存后就是三段 `fixed` + 一段单缸型 `ladder`。

### 4.2 判定与换算

```
规则继承：skuVatRules[skuId] → spuVatRules[品名] → defaultVatRuleId（缺失时取第一条规则）→ 没有规则才按公斤精确下单
命中分档：按判据取指标，从低到高取第一条「上限为空 或 指标 ≤ 上限」的档（上下限都算在区间里，边界值归前一段：120 属于「不超过 120」）
换算动作：
  skip   → 0 公斤（不下单）
  ladder → 按缸型就近取整（推荐，见下）
  fixed  → 固定下单量（视为 1 缸）
  vat    → 缸数 = 需安排 ÷ 每缸公斤，再按零头策略取整；下单量 = 缸数 × 每缸公斤
  round  → 同 vat，但每缸公斤 = 取整步长（10 = 整十，100 = 整百）
零头策略：nearest（默认，余量 ≥ 阈值补一缸）/ floor（只下整缸）/ ceil（不足一缸也下一缸）
下限保护：需求 > 0 时缸数至少为 minVats（默认 1 缸）
```

`ladder` 的两条分支（缸型 `sizes` 升序，`top` = 最大缸型）：

```
需求 ≥ top：缸数 = 需求 ÷ top，按零头策略取整（nearest = 余量 ≥ 半个大缸补一缸）；下单量 = 缸数 × top
需求 < top：取 |需求 − 缸型| 最小的那一种（正好一半时取大缸），只下 1 缸
```

> 也就是说 `ladder` 是「就近到最近的整缸，正好一半向上」，多缸型时会自己推导出区间（80 / 160 / 240 → 断点 120 / 200 / 360）。
> 现在界面只用它的一种用法：**末行单缸型**（`sizes` 只有一个值），前面各行一律 `fixed`，所以「补到 80 / 160 / 240」由区间直接决定，不再靠 `ladder` 去猜；老的多缸型 `ladder` 规则打开编辑时会被摊成对应的区间行。

- 入口函数：`planOrderQuantity(need, rule, context)`，返回 `{ action, bandText, kgPerVat, rawVats, vatCount, rounded, remainderKg, deltaKg, deltaRate, warnings }`。
- 下拉候选：`vatQuantityOptions(rule)`，返回每个缸型一项 `[{ quantity, vatCount: 1, kgPerVat }]`（升序，就是规则里的单缸重量）。
- 规则解析：`resolveVatRule(settings, { skuId, product })`；分档查询：`resolveVatBand(rule, context)`。
- 规则文案：`describeVatBands(rule)`（`ladder` 会展开成它推导出的区间）/ `summarizeVatRule(rule)` / `describeVatRemainder(rule)`。

### 4.3 默认两条规则

| 规则 | 区间与补法 |
| --- | --- |
| 标准大货补单（默认） | 0–120 公斤 → 补到 80 · 121–200 公斤 → 补到 160 · 201 公斤以上 → 每缸 240 公斤，多缸就近取整 |
| 小批量补单 | 0–50 公斤 → 补到 0（不下单）· 51 公斤以上 → 每缸 60 公斤，多缸就近补整 |

编辑弹窗里一条规则就是**一行一段**：`从 [下限] 到 [上限] → 补到 [公斤数]`，**两端都算**——所以三行填出来是 `0–120 / 121–200 / 201–不限`，下一行的「从」= 上一行的「到」+ 1（改任一边另一边跟着走）。最后一行没有上限，只有它会在超过自己的公斤数时按这个数一缸一缸往上补（240 → 480 → 720…）。**补到 0 就是这一段不补**，所以弹窗里没有「不补 / 整十」这类选项；区间必须连续（上限不能小于下限），断了就地标红并拦住保存。老配置里的「不补」段打开后就是一行「补到 0」，老的「整十 / 整百取整」段没法用「补到」表达，打开时直接并进上一段。

两者都可由生产人员在「设置 → 下单配置 → 缸规则」改；改完要点「确定」才落盘。

### 4.4 换算示例（默认「标准大货补单」：0–120 补 80 / 121–200 补 160 / 201 以上每缸 240）

| 需安排（公斤） | 建议下单 | 说明 |
| --- | --- | --- |
| 20 | 80（1 缸 × 80） | 落在 0–120 这段 |
| 100 | 80（1 缸 × 80） | 同上 |
| 120 | 80（1 缸 × 80） | 正好是这一段的上限（两端都算） |
| 121 | 160（1 缸 × 160） | 进到 121–200 这段 |
| 150 | 160（1 缸 × 160） | 同上 |
| 200 | 160（1 缸 × 160） | 正好是这一段的上限 |
| 201 | 240（1 缸 × 240） | 进到 201 以上这段 |
| 300 | 240（1 缸 × 240） | 余量 60 < 半个大缸（120），舍弃 |
| 360 | 480（2 缸 × 240） | 余量 120 = 半个大缸，补一缸 |
| 500 | 480（2 缸 × 240） | 余量 20，舍弃 |
| 3371 | 3360（14 缸 × 240） | 余量 11，舍弃；比需安排少 11 公斤 |

> 一张分订单**只用一种缸型**，不做拼缸：400 公斤下 2 × 240 = 480，而不是 160 + 240 = 400。跨染厂拆成多张分订单时，每张单可以各用一种缸型。
>
> 文案差异：`ladder` / `vat` 才叫「每缸 X 公斤」；`round` 显示「按 X 公斤取整」，`fixed` 显示「固定 X 公斤/单」——避免把「按 100 公斤取整」误读成 100 个缸。

### 4.5 与备货口径的边界（重要）

- 主面板「需安排」、批量 / 紧急补货的建议值 **永远是精准公斤数**，不取整缸。
- 缸规则只作用于：采购下单页（左侧列表的规则参数、右侧进度条的 hover 提示、按缸方式的缸型候选与建议值、按缸下单量换算）与清单导出文件里的建议缸数列。
- 「缸型（公斤）」候选列出规则里的单缸重量（1 缸），也允许手输自定义缸型；多缸靠「缸数」列乘。
- 每张分订单独立选「按缸」或「按公斤」：按缸时下单量 = 缸数 × 缸型；按公斤时直接输入公斤，缸数 / 缸型不适用，不计入缸数合计。
- `vatCount` / `kgPerVat` 只保存按缸分订单的快照；按公斤分订单只保存明确的 `quantityMode` 与下单量，避免把偶然整除的自由公斤误认为按缸。
- 改缸规则**不会**回溯已保存的分订单；已落盘的 `vatCount` / `kgPerVat` 是快照。

## 5. 设置 · 下单配置（`/config` 左栏「下单配置」）

与「备货配置」同在一个设置壳里，点左栏分区切换；顶部工具条跟着域切换。旧的 `/purchase/settings` 深链会自动跳到 `/config?panel=vat`，直接落到缸规则。

页面用**草稿**编辑，顶部「确定」才落盘，「放弃」丢弃改动；`有未保存的修改` 状态由设置快照对比得出。点击「确定」前会校验缸规则（区间无缝、末档无上限、参数大于 0 等）。

| 分区 | 作用 |
| --- | --- |
| 缸规则 | 规则列表（一条规则占两行：第一行是名字 + 右侧「设为默认」单选 + 编辑 / 删除，第二行是 `0–120 → 80 kg │ 121–200 → 160 kg │ 201 以上 → 240 kg`）；默认规则左侧一道主色竖条、不能删除；新增 / 恢复默认两条；编辑弹窗是**一段一行**（左侧标签写作「范围1 / 范围2 …」）：`从 [下限] 到 [上限] → 补到 [公斤数]`（两端都算，三行写出来是 0–120 / 121–200 / 201–不限），下一行的「从」= 上一行的「到」+ 1，末行无上限，补到 0 = 不补，区间不连续就地标红；**要在中间细分时用行内「插入」**——把这一段从中间一分为二（原段留前半、新段接后半并沿用原段的补到量），只有这一段变化，后面的范围不用重调；底部「＋ 添加范围」= 在最末的开口段后面再加一段；分段依据 / 零头策略 / 至少几缸不在界面上暴露，一律用方案里的默认值；底部一个试算输入 + 结果 |
| 品名绑定 | 这排单选**只管「看哪一桶」**，跟规则行上的「设为默认」互不影响：`默认 1545`（没单独绑定的）、每条规则一个（单独绑定的）、`不取整`；数字是**显式绑定数**，所以改默认规则不会搬动任何品名。下面自适应列宽的网格列出这一桶的品名；点任意品名弹浮层改归属（选「默认」= 解除绑定，点浮层外面关闭）；搜索框跨规则查找并在格子里标出当前归属，底部「全部归到…」可一次改掉全部命中 |
| 染厂管理（左栏合并入口） | 同一页上下展示「染厂清单」与「染厂与 SKU 关联」两个配置区。染厂清单默认收成一行名称摘要，过长省略；点击打开管理弹窗，可新增、删除、导入染厂；名称在清单行内点编辑后直接输入，并用「确认 / 取消」收束本次修改；启用状态用开关在状态列直接切换。染厂清单是分订单染厂下拉的来源；停用的染厂不出现在下拉里，但已有分订单保留原厂名。关联区以染厂为主视图，左侧数字表示该染厂已有的明确 SKU 关联数（不是全部可生产 SKU 数），右侧只显示明确限制到该染厂的 SKU；未配置 `skuFactories[skuId]` = 全部启用染厂可选。把一个未限制 SKU 加入某染厂会将它限制为当前选择的染厂（也可再配置其他染厂），这是有意收窄范围，不是追加到原来的「全部」。解除最后一个显式染厂后会删除该限制，恢复全部启用染厂可选。添加入口统一放在页面上方，操作对象明确为当前选中的染厂；空状态只解释默认可选口径，不重复放添加按钮。支持导入「染厂名称 + SKU唯一标识」Excel，也认「染厂名称 + 产品名 + 颜色」（按 `品名|颜色` 拼成 SKU 键）；右上角「导出模板」直接下载这份 5 列表头（染厂名称 / 产品名 / 颜色 / 染厂色号 / 备注），后两列仅供参考、导入不落库。预览区区分新增、已存在、文件重复、未匹配及未限制 SKU 的范围收窄确认，只有确认后才应用有效新增行。TXT 本身没有系统 SKU 标识；以 TXT 出现的染厂为准维护染厂清单，按去空格后的 `品名|颜色` 生成 SKU 键，当前去重数据为 8 家染厂、525 个 SKU 键、550 条染厂关系；演示库存使用相同键格式但不补造 TXT 中的库存行。历史订单与草稿按确认清空后，源码文件、本机 localStorage 与 IndexedDB 均为空 |
| 人员与分类（左栏合并入口） | 同一页上下展示「人员名单」与「分类分配」两个配置区。人员名单维护下单可选的员工总名单，以人名小卡片展示（删除时同步清掉各分类里的同名分配）；分类分配让一个 SKU 只属于一个分类，并从人员名单选择该分类的分单人员；可从产品资料导入「树形分类」列 |

顶部还有「导入设置文件 / 导出设置文件」（`purchaseSettings.json`，含缸规则）。

## 6. 分订单的选项口径（`resolve.js`，页面不要各写一份）

| 函数 | 口径 |
| --- | --- |
| `factoriesForSku(settings, skuId)` | 该 SKU 配了可选染厂 → 只列这些（未启用的剔除）；没配或配的都被停用 → 回退全部启用染厂 |
| `categoryForSku(settings, skuId, importedCategory)` | 人工覆盖（`skuCategoryOverrides`）优先，其次导入行自带分类 |
| `assigneesForCategory(settings, category)` | 该分类勾选的人员 |
| `assigneesForSku(settings, skuId, importedCategory)` | 分类有人 → 只列分类人员；分类没配人 → 回退分单人员表全部人员 |
| `summarizeOrders(entries)` | 一次下单的合计 `{ total（公斤）, counted（张数）, vats（缸数） }`，只统计 `quantity > 0` 的行 |
| `buildOrderIndex(orders)` | 按 `skuId` 聚合 `{ ordered, received, pending, count, vats }`，**只累计 `status = active`**；主面板「备货」列只读它 |
| `findFactoryById / findFactoryByName` | 染厂临时手输时回填 `{ factoryId, factoryName }`；手输的新厂名只用于本次下单，不写回设置 |

## 7. 数据与持久化

| 数据 | 存放 | 刷新后 | 备注 |
| --- | --- | --- | --- |
| 设置 · 下单配置（含缸规则） | `src/purchase/settings.json` + localStorage `purchase-settings:v1` | ✅ | 开发态写 `settings.json`（端点 `/__purchase-settings/save`），构建产物只写 localStorage |
| 草稿 + 订单 | IndexedDB `documents.purchaseOrders`（整份 v2 文档） | ✅ | 不再受 localStorage 5 MB 限制；开发态仍顺带写 `orders.dev.json` 调试镜像（种子 `orders.json` 为空）；写入失败会在界面提示，不再静默丢单 |
| 需安排（`planned`）与锁态 | IndexedDB `meta.workspace`，**按 `skuId`** | ✅ | 锁定态由撤销快照派生，一并持久化；重新导入后自动挂回新行 |

| 撤销快照（`plannedUndoHistory`） | IndexedDB `meta.workspace`，按 `skuId` | ✅ | 刷新后仍可撤销；`pagehide` 时会把未落盘的改动 flush 一次 |

> 也就是说：**「这次要采购哪些 SKU」和「人的备货决定」都会留下来**，导入的库存与销售表另有快照（见 [数据持久化方案](./数据持久化方案.md) 第 10 节）。
> 需要留痕的是三个动作：确认下单、修改、撤销/作废 —— 分别由 `submittedAt`、`revisions[]`、`status + cancelledAt` 记下来，不做物理删除。

## 8. 关键不变量（改代码前先看）

1. 需安排**只**通过 `writePlanned`（行内采纳 / 批量补货 / 紧急补货共用）写入，不要另开写入口。
2. 分订单**只**以唯一标识为键；不要用行 `id`（导入会重排）。**采购下单的列表直接由 `planned > 0` 派生，不要再引入第二份清单状态。**
3. 缸规则**只**在 `src/purchase/vat.js` 实现；页面拿到 `planOrderQuantity` 的结果直接用，不要自己再算一遍。
4. 主面板不取整缸；缸只出现在下单环节与导出。缸型就近取整只在 `vat.js` 的 `ladder` 分支实现。
5. 主面板表格里只有「需安排」可编辑；品名 / 颜色 / 生产中（生产排单进仓重量）/ 欠货 / 周消耗 / 周转入 / 在仓都是导入值，只读；「在途库存」不是导入值，与「累积下单」同源（订单流水累计下单公斤），同样只读。
6. 分订单编辑器只有一份（`SkuOrderEditor.vue`），只在 `/purchase` 使用。
7. 设置是草稿编辑，未点「确定」不落盘；缸规则在保存前会整体校验。
8. 空白分订单行运行时保留、落盘丢弃（`keepBlankEntries`），别再改成统一丢弃。
9. 示例数据区（`/example`、`/example/config`）不参与这套流程，也不要改。
10. 规则判定是「上限递增、末档无上限」；改分档时只改上限，文案会跟着重算。
11. **累积下单 / 到货只统计 `status = active` 的订单**；撤销（`cancelled`）保留行但不参与任何统计，不得物理删除。
12. **到货只追加 `receipts`**，`receivedQty` 由它求和派生；不允许覆盖写。撤销到货 = 撤掉最后一条。
13. **确认下单 = 需安排清零 + 锁解除**；**撤销订单 = 该单公斤回补到未锁的需安排**。两者方向相反，别写反。
14. **累积下单是留痕，不参与预计库存**：预计库存只有 `在仓 + 在途 + 需安排` 一处（见第 17 条）；主面板只把它当「下过单」显示，别拿它算在途或预计。补登记到货上限 = 该单「下单 − 已补登」，超收直接拦下。
15. 已有到货记录的分订单，撤销前必须二次确认。
16. 下单历史可永久删除整批或单张分订单；订单及其 `receipts` / `revisions` 一并删除。有效单删除后由库存建议公式重新计算需安排，不把订单公斤数直接回填；已作废单删除不重复回补。
17. **同一批货只能算一次**：接上在途对账后，`producing` / `ordered` 不得再单独加进预计库存；预计库存只有 `在仓 + 在途 + 需安排` 一处。
18. **在途只来自 `src/purchase/inTransit.js`**：页面 / store 不要自己拿 `ordered` 或 `producing` 拼在途。
19. **退货入库不算到仓**：它只增加在仓，不能冲掉采购单的在途。

## 9. 常见操作

| 想做的事 | 怎么做 |
| --- | --- |
| 改缸型（把补货量归到 80 / 160 / 240 三档） | 设置 → 下单配置 → 缸规则 → 编辑规则：一行一段填 `从 0 到 120 补到 80`、`从 121 到 200 补到 160`、`从 201 到 不限 补到 240`（两端都算，下一行的「从」自动 = 上一行「到」+ 1） |
| 只用一种缸（如每缸 240 公斤） | 只留一行：`从 0 到 不限 补到 240`（超过 240 时按 240 一缸一缸往上补）；老配置里的「按每缸公斤取整」打开后同样显示成单缸型的一行 |
| 某一段不补（如 50 公斤以下不下单） | 那一行的「补到」填 `0`，这一段就 0 公斤、不进下单列表 |
| 某个品名不按缸取整 | 设置 → 下单配置 → 缸规则 → 品名绑定里点该品名 → 选「不取整」 |
| 只让个别小批量品名走小批量规则 | 品名绑定里点该品名 → 选「小批量补单」；或搜索后点底部「全部归到…」一次套用 |
| 某个 SKU 单独例外 | 目前界面只到品名级；SKU 级可通过 `skuVatRules`（设置文件）配置，值填规则 id 或 `__none__` |
| 看某条规则会影响多少品名 | 品名绑定那排单选标签上的数字；改默认规则前先看规则行左侧的主色竖条 |
| 撤销刚采纳的需安排 | 主面板该行点「撤销」（仅未刷新时有效） |
| 看某个 SKU 下了多少、到了多少 | 主面板入口组的「下过单」（累计下单公斤，只增不减）；到没到仓看「在途库存」（归零 = 已到仓）与「在仓库存」；点「在途库存」行尾图标看逐张分订单 |
| 补登记到货 | 分订单明细弹窗里那一行 `⋯` → 补登记到货：填公斤（≤ 该单剩余），在途当场扣掉；正常情况不用它，导入的生产入库会自动对账 |
| 补登记记错了 | 目前只能在 `⋯` → 改单 / 撤销整单里纠正，或等导入生成正确的生产入库后在途自然归零（按单撤回到货的界面已随滚动导入下线） |
| 剩下的货不要了 | 分订单明细弹窗 `⋯` → 撤销整单：该单作废、公斤数回补到需安排（未锁草稿） |
| 下单量填错了 | 订单弹窗左列「改单」：输入新公斤数（不能少于已到货），会留一条 revision |
| 撤掉一张下错的单 | 订单弹窗左列「撤销整单」：该单作废、公斤数回补到需安排（未锁），预警退回红色，重新采纳即可再下 |
| 确认下单后主面板为什么还是红 / 黄 | 需安排已清零解锁；预警只比预计库存（在仓 + 在途 + 累积下单 + 需安排锁定）。仍红 / 黄说明累计下单还没把预计库存顶到绿色带，需安排格里的建议值就是「还差多少」，按它再下一单即可 |
| 交给染厂下单 | `/purchase` 工具条「导出待下单」，分单明细带染厂、人员、缸数、数量、到货、备注 |
| 导出已经确认的单 | `/purchase` 页头「导出订单」：本次确认批次 / 今日已确认 / 自定义日期范围；确认后已从左侧列表移走的单也在 |
| 按日期导出历史 | `/purchase/history` 选「按月 / 按日 / 自定义范围」再点「导出 Excel」，导出当前筛选结果 |
| 清空某 SKU 的分订单 | `/purchase` 右侧「清空分订单」（二次确认） |

## 10. 已知边界

- 需安排（含锁态）已随 IndexedDB 持久化：刷新 / 重开浏览器后仍在，重新导入时按 `skuId` 自动挂回新行；**订单、累积下单、到货一直不会丢**。
- 累积下单按有效订单累计；撤销整单或在下单历史物理删除有效单都会减少它。手工「补登记到货」仍写 `receipts`，与导入的生产入库一起算到仓累计；界面不再展示逐条到货记录（导入只有 SKU 级生产入库，按单到货还原不出来）。
- 到仓以导入的出入库明细为准：`在途 = max(0, max(下单累计, 排单累计) − 生产入库累计 − 手工补登累计)`；手工补登只用来在导入没跟上（或来源单据名称没匹配上）时兜底，**不动在仓库存**。
- 需要"到没到仓"的准确判断时看主面板「在途库存」，不要看「下过单」（它是留痕，只增不减）。
- 撤销订单回补的需安排是**未锁草稿**，不会自动恢复成原锁定值；要重新生效必须再点「采纳」或重新补货。
- 部分到货（待收 > 0）不阻塞下一次补货：同一 SKU 可以有"还有 500 没到"和"又补了一批"并存，靠订单弹窗逐张核对。
- 分订单数量不做「跨染厂整缸校验」：各分订单分别按缸数录入，合计可以略高于需安排（取整差额），界面会显示差额。
- 不做拼缸：一张分订单只用一种缸型，要混装只能拆成多张分订单（合计仍可能不是整缸组合）。
- 同行备注里的缸号是自由文本，系统不解析、不校验唯一性。
- 订单平时按流水追加，改单留 `revisions`、到货保留 `receipts`；用户可在下单历史明确确认后物理删除订单及其关联记录。系统没有跨人的权限与审批；多人协作、认领与入库自动核销按 [数据持久化方案](./数据持久化方案.md) 阶段二再演进。
