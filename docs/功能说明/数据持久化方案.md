# 数据持久化方案（工作文档）

> 目标：让系统的业务数据在刷新 / 关浏览器 / 重开电脑后不丢，并支持「完整订单记录」（约 3 万行流水）。
> 路线：**阶段一先做单机版（零服务）**，但数据访问层按可替换来设计，**阶段二**再平滑升级到多人协作版。
> 明确不引入：Python、MySQL。

---

## 1. 结论先行

| 问题 | 结论 |
| --- | --- |
| 3 万行订单，纯 Vue 扛得住吗？ | **扛得住**。3 万条对象约占 20–30 MB 内存，全量筛选 + 排序 < 10 ms，表格已有虚拟滚动。 |
| 一定要开 Python 吗？ | **不需要**。清洗引擎是 JS（`tools/cleaning/engine.mjs`），上 Python 等于重写一遍，纯亏。 |
| 一定要装 MySQL 吗？ | **不需要**。多人版用 **Node + SQLite 单文件**，30k 行 + 内网几十人绰绰有余，备份就是复制一个 `.db`。 |
| 那要改什么？ | 真正的问题不是「量」，而是 **① 存储介质选错 ② 大部分业务数据根本没持久化 ③ 订单模型是覆盖快照而非流水**。 |

## 2. 现状盘点

### 2.1 各类数据现在存在哪

| 数据 | 当前存放 | 刷新后 | 3 万行时的体积 |
| --- | --- | --- | --- |
| SKU 库存总表（导入结果） | Pinia 内存 `inventoryItems` | ❌ **丢失，要重新导入** | 约 30 MB |
| 销售表 1–12 月条数 / 重量 | Pinia 内存 `salesSheet`（shallowRef） | ❌ 丢失 | 约 10 MB |
| 采购清单 `purchaseList` | Pinia 内存 | ❌ 丢失 | 小 |
| 「需安排」+ 撤销快照 | Pinia 内存 | ❌ 丢失 | 小 |
| 分订单 `orders` | localStorage + 开发态 JSON 文件 | ⚠️ 保留，但**超 5 MB 会静默失效** | 10–20 MB |
| 下单设置 `settings` | localStorage + JSON 文件 | ✅ | 4 KB |
| 备货配置 `profiles` | localStorage + JSON 文件 | ✅ | 6 KB |
| 手动策略 `manualSkus` | localStorage + JSON 文件 | ✅ | 小 |
| 隐藏 SKU `hiddenSkus` | localStorage + JSON 文件 | ✅ | 小 |

来源：`src/stores/inventory.js`（无任何 load/save）、`src/purchase/persistence.js`、`src/stocking/persistence.js`。

**结论：目前只有「配置类」和「分订单」做了持久化，业务主数据（导入的库存、销售表、采购清单、需安排）全是内存态。**

### 2.2 两个必须修的风险

1. **localStorage 装不下 3 万行订单。**
   `saveOrders()` 把整份 JSON 一次性 `localStorage.setItem`。3 万行约 10–20 MB，而 localStorage 单源上限约 **5 MB**，必然抛 `QuotaExceededError`。
   `writeCache()` 的 `catch` 只打了 `console.warn` —— 界面显示保存成功，刷新后数据没了，**属于静默丢单**。

2. **订单是「按 SKU 覆盖的快照」，不是流水。**
   `orders[skuId] = [条目…]`，改一次就整组覆盖，没有时间、没有状态、没有历史。
   要「完整的订单记录」，数据模型得从 **map 改成 append-only 的 table**。

## 3. 分层设计（关键）

所有页面**不直接碰存储**，只调用同一个数据访问层（repository）。存储实现在下面切换时，页面代码一行不用改。

```
Vue 视图 / Pinia store
        │  只调这些方法：
        │  listOrders() / appendOrder() / claimTask() / saveImport() …
        ▼
src/data/repo.js          ← 接口约定（唯一对外契约）
        │
        ├── src/data/indexedDbRepo.js   ← 阶段一：本机 IndexedDB
        └── src/data/httpRepo.js        ← 阶段二：fetch → Node → SQLite
```

### 关于「IndexedDB 那层换成 API 调用」是什么意思

数据库分两类位置：

- **进程内嵌**：IndexedDB（浏览器进程里）、SQLite（一个文件，被进程直接读写）。它们没有网络端口，只有**本地函数调用**。`indexedDB.open()` 本身就是浏览器给你的 JS API，但它只对**这个浏览器、这个源**可见。
- **独立服务**：MySQL 是单独一个进程监听 3306 端口，所以任何客户端（网页、Python、Navicat）都能连。

所谓「换成 API 调用」，指的是 **repo 的实现换了，调用它的人没换**：

```js
// 阶段一：本地实现
export async function appendOrder(order) {
  return idb.put('orders', order)
}

// 阶段二：网络实现（签名完全一样）
export async function appendOrder(order) {
  const res = await fetch('/api/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(order),
  })
  return res.json()
}
```

页面里永远是 `await appendOrder(...)`。至于是写进了这台电脑的浏览器数据库，还是发给 Node 写进 SQLite，**页面不知道也不需要知道**。这就是「随时能升级到多人版」的全部含义。

## 4. 阶段一：单机版（先做这个）

**前提**：只有你一台电脑、一个浏览器。零服务，`npm run dev` 或静态部署都能跑。

### 4.1 存储选型

统一用 **IndexedDB**（不要用 localStorage 存业务数据）：

- 配额约为磁盘剩余空间的 60%，几百 MB 是常态；
- 支持索引，按日期 / SKU / 染厂查询；
- 异步，不阻塞主线程。

实现方式二选一：

- **A（推荐先做）**：手写 `indexedDbRepo.js`，约 150 行，无新依赖；
- **B**：上 `idb` 或 `Dexie` 简化代码。数据量大到要做 SQL 聚合时，再考虑 `sql.js`（浏览器内 SQLite，持久化到 IndexedDB）。

### 4.2 数据库结构

```
DB: kucun-persist   version: 1

store: orders          keyPath: id      index: bySku, byMonth, byBatch, byStatus
store: orderStats      keyPath: month   （按月预聚合：条数 / 数量 / 金额，避免每次全量扫）
store: tasks           keyPath: id      index: byStatus, bySku
store: purchaseList    keyPath: id
store: inventoryItems  keyPath: id      index: bySku
store: salesSheet      keyPath: panelKey
store: snapshots       keyPath: id      （导入批次，**只保留最近 5 份**，滚动淘汰）
```

> 按月统计走 `byMonth` 索引；订单表增长到几十万行后，统计只读 `orderStats`，不扫明细。

### 4.3 订单流水模型

```js
{
  id,            // 主键，前端生成（时间戳 + 随机）
  batchId,       // 一次「确认下单」生成的批次号，同批多个 SKU 共用
  taskId,        // 关联的采购任务（多人版起有意义，现在可为空）
  skuId,         // 唯一标识
  product, color,
  factoryId, factoryName,
  assignee,      // 分单人员
  quantity,
  vatCount, kgPerVat,
  note,
  status,        // 'draft' | 'confirmed' | 'producing' | 'received' | 'cancelled'
  month,         // 'YYYY-MM'，写库时生成，供按月索引统计
  createdAt, updatedAt,
  confirmedAt,   // 确认下单时间
  receivedAt     // 到货时间（由导入对账填，不手工填）
}
```

> 「订单记录」= 这张表的一行。写入只追加（append-only），修改留 `updatedAt`，作废用 `status = 'cancelled'`，**不物理删除**。

### 4.6 主数据快照：既「进去就有数据」，又保留导入

**结论：导入流程一行都不改，只把它的「终点」从内存改成内存 + 快照。**

启动加载：

```
有快照 → 载入最新快照 → 叠加计划层（需安排 / 采购清单）→ 渲染
无快照 → 用 src/data/inventoryItems.js 种子（保持现在的「进去就有数据」）
```

导入：

```
选文件 → 解析（现有 pipeline 不动）→ 写入 Pinia
                                 → 生成快照（gzip）落库
                                 → currentSnapshotId 指向它
                                 → 裁掉第 6 份
```

**快照只存事实层**（导入的库存 + 销售表）。计划层与执行层单独存，按 `skuId` 挂接：

| store | key | 为什么单独存 |
| --- | --- | --- |
| `snapshots` | snapshotId | 导入数据，可回滚 |
| `plans` | skuId | 需安排是人的决定，不该随快照回滚 |
| `purchaseList` | skuId | 同上 |
| `orders` | orderId | 订单流水，append-only |

**为什么不把 `planned` 塞进快照**：一旦塞进去，「回滚到上周的导入」会把你这周做的备货决定一起回滚掉。分开存，回滚只回滚事实，人的决定保留；切快照时按 `skuId` 重新挂接，挂不上的进「未匹配」清单供人工清理。

**体积**：3 万行总表 + 销售表约 40 MB JSON，gzip 后约 4–6 MB；5 份约 25 MB，IndexedDB 毫无压力。
**去重**：同一份文件重复导入时（内容哈希相同）不新建快照，只更新时间，避免 5 个名额被同一份数据占满。
**回滚**：导入弹窗里给一个「历史快照（最多 5 份）」列表，点一下就切回去。

## 5. 订单确认后的业务闭环（建议稿，**未定稿**）

现状的业务链到「下分订单」就断了：

```
导入 → 评分 / 预警 → 批量或紧急补货 → 需安排 + 采购清单
     → 下分订单（自动保存，没有确认动作）→ 【到此为止】
```

三个缺口：

1. **没有「确认」动作**：随手填的两行草稿，和已经发给染厂的正式单，混在同一份数据里；
2. **已下单量不回写**：主管看到「需安排 1000」，但不知道下单员只落实了 700；
3. **下单之后没有闭环**：到货、入库、核销全靠另开 Excel。

### 5.1 完整流程总览（草案，待确认）

```
① 导入
   主面板 / 销售表：一次选「总表 + 销售表」
   分表入口：产品资料 / 出入库明细 / 库存结存 / 欠货 / 生产排单
        ↓ 清洗（tools/cleaning/engine.mjs）
        ↓ 生成【快照】= 事实层，可回滚，保留最近 5 份
② 评估
   模式命中 → 评分档 → 系数 → 红线 / 正常 / 峰值
   指标：日库销比（天数）或预计库存（公斤）
        ↓
③ 主管决策（主面板）
   批量补货：勾选 SKU → 默认「补至正常库存 × 80%」→ 确认
   紧急补货：红色预警行 → 填追加量
        ↓ 覆盖写「需安排」+ 写入「本次采购清单」（同一 SKU 一条）
④ 下单员执行（/purchase）
   左侧：本次采购清单（只来自已采纳的需安排）
   右侧：按染厂拆「分订单」= 染厂 / 分单人 / 数量 / 缸数 / 每缸公斤 / 备注
        ↓ 自动保存 = draft（草稿）
        ↓ 【新增】确认下单 = confirmed + batchId（锁定；要改先撤回）
⑤ 对账（主面板新增两列）
   已下单量 / 待下单量 = max(0, 需安排 − 已下单) / 超下单量
        ↓
⑥ 生产（待定）
   染厂回传 → producing
        ↓
⑦ 到货（待定）
   下一次导入库存结存表 → 在途 / 在仓增加 → received
   差异提示：confirmed 超过 N 天、在途没涨 → 疑似未到货
        ↓
⑧ 归档
   订单流水按月统计（orderStats）
```

> ①②③④⑤ 是本次持久化要落地的最小闭环；⑥⑦⑧ 的数据来源见第 9 节。

### 5.2 核心原则：三层数据，绝不互相覆盖

| 层 | 数据 | 谁写 | 可变性 |
| --- | --- | --- | --- |
| **事实层** | 在仓 / 在途 / 生产中 / 欠货 / 周转入 / 销售 | Excel 导入 | 只读，下次导入整体覆盖 |
| **计划层** | 需安排 `planned` | 主管 | 可改，带撤销快照 |
| **执行层** | 订单记录（批次 + 明细 + 状态） | 下单员 | append-only + 状态流转，不覆盖 |

### 5.3 「扣回待备货」不要扣 `planned`

`planned` 是主管的原始决定，是审计依据。如果下单后把它减掉：

- 「当初计划多少、下了多少、还差多少」就永远答不出来了；
- 一旦要撤回 / 改单，得反算回去，容易算错；
- `planned` 本身会被 `applyRestockPlans` 覆盖写，扣减结果也保不住。

**正确做法是派生对账值，三个数并存**（都不落库，实时算）：

```
已下单量 = Σ(该 SKU 状态 ∈ {confirmed, producing, received} 的明细数量)
待下单量 = max(0, planned − 已下单量)      ← 「扣回待备货」要的其实是这个
超下单量 = max(0, 已下单量 − planned)      ← 现实常有，别让它被负数藏起来
```

主面板加一列「已下单」，或者把「需安排」显示成 `1000 / 700`。这比"把 1000 改成 300"信息量大得多，而且**一个导入字段都不动**。

### 5.4 「加入其它数据」= 把预计库存的构成拆开

现在 `projectedStock = 在仓 + 在途(导入) + planned`（见 [utils/inventory.js](d:/Ghaniyy/Code/Demo/网布表格/kucunyujing1.1/src/utils/inventory.js)），数值没错，但看不出「有多少是真的在路上」。建议拆成：

```
预计库存 = 在仓 + 已导入在途 + 已确认下单未到货 + 未下单需安排
                                    └── 确定 ──┘   └── 计划 ──┘
```

总数不变，但能回答「这批到底多少是确定的」。

### 5.5 状态机

```
draft（草稿，自动保存，可改）
   │ 确认下单
confirmed（已下单，锁定；要改必须先「撤回」回 draft）
   │ 染厂回传
producing（生产中）
   │ 由下一次导入的在途 / 在仓变化体现，不手工填
received（已到货）
   │
cancelled（作废：保留记录，不物理删除）
```

- 确认时生成 `batchId`，一次确认多个 SKU 共用；
- 撤回要留痕（记 `updatedAt` + 一条撤回记录），不允许无声改单。

### 5.6 到货不要手工填

在仓 / 在途是导入值，顺序应该是：**染厂发货 → 下一期库存结存表里出现 → 系统导入后自动对上**。
系统只做差异提示：`confirmed` 超过 N 天、导入的在途仍没增加 → 标「疑似未到货」。否则会出现系统库存和 Excel 库存两套数字打架。

### 5.7 为什么这件事要排在持久化前面

「确认」一旦存在，订单就必须是 append-only 流水（谁、何时、确认了多少、什么状态），而不是现在这种「按 SKU 整组覆盖的快照」。这和第 2.2 节的结论是同一件事：**数据模型对了，3 万行 / 月的统计才有意义**。

## 6. 阶段二：多人版（**暂不实施**，只留接口）

> 决策：现阶段（2026-11-13）不考虑多人版。本章保留原因只有一条——**阶段一的代码不要写死成本地存储**，将来真要做时只需加一个实现文件。接口含义见第 3 节。

**触发条件**：主管在主面板操作、下单员在下单面板操作，两个人两台电脑要看同一份数据。

这本质上不是「存储」问题，而是**共享状态 + 任务交接（handoff）**问题：主管点「需安排」→ 生成待下单任务 → 下单员看到并认领 → 填染厂 / 分单 → 主管看进度。IndexedDB 只活在一台机器的一个浏览器里，做不到。

### 6.1 技术选型

| 部件 | 选择 | 理由 |
| --- | --- | --- |
| 服务 | **Node + 原生 `node:http` 或 Express** | 项目本来就是 Node，且能直接 `import` 复用 `tools/cleaning/engine.mjs` |
| 数据库 | **SQLite 单文件**（Node 22+ 自带 `node:sqlite`） | 无需安装服务、无需账号、备份=复制文件；30k 行毫无压力 |
| 部署 | 内网一台机器跑 `node server.mjs`，其他人浏览器访问 `http://<内网IP>:3000` | 主管 / 下单员天然共用一份数据 |
| MySQL | **不用**，除非将来要接 ERP 或多人高频并发写 | 装服务、开端口、建库、配账号、写迁移，收益不成正比 |

### 6.2 接口草案

```
GET    /api/orders?skuId=&status=
POST   /api/orders                 追加一条订单记录
PATCH  /api/orders/:id             修改 / 作废
GET    /api/tasks?status=pending
POST   /api/tasks                  主管创建待下单任务
POST   /api/tasks/:id/claim        下单员认领（乐观锁）
POST   /api/tasks/:id/complete
GET    /api/snapshots/latest       主数据快照（库存 / 销售表）
PUT    /api/snapshots/:key
```

### 6.3 身份与协作

- 不做复杂登录：本地保存「当前操作人」（姓名 + 角色：主管 / 下单员），请求带在 header；
- 任务认领用**乐观锁**：`UPDATE tasks SET claimed_by=? WHERE id=? AND claimed_by IS NULL`，避免两人抢同一单；
- 冲突策略：**服务端时间戳 last-write-wins** + 订单只追加不覆盖（真正会冲突的只有「需安排」数量，按整行覆盖即可）；
- 主数据（库存 / 销售表）由主管导入，写 `snapshots`，其他人只读最新版本。
