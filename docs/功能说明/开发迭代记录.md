# 布料库存规划 Demo｜开发迭代记录

按阶段记录从截图原型到当前 Demo 的实现与口径变更，每条只留结论；验证一律为「`npm run build` 通过 + 浏览器或 Node 实测」，不再逐条罗列。现行口径以[需求文档1.1](../需求文档/需求文档1.1.md)、[模式与系数设置](./模式与系数设置.md)、[数据清洗规则](./数据清洗规则.md)、[采购下单流程](./采购下单流程.md)为准。

## 一、原型与早期交互（1–13）

- **1 起点**：Element Plus 静态库存表 → Vue 3 + Element Plus + Pinia + Router，导出用 fflate 在浏览器内组装 XLSX；数据只在内存，刷新回初始。
- **2 表格原型**：分组表头（商品 / 入口 / 出口 / 库存 / 数据反馈）＋模式系数算红线 / 正常 / 峰值，预警四色（紧急红 / 降低库存紫 / 无需补货绿 / 常规补货黄），系数缺省不参与判定。
- **3 分组与共享数据**：品名父行 → 颜色子行可折叠，父行汇总数量、缺口率与库销比按汇总分子分母重算；主面板 + 配置页共享 Pinia，切路由不丢修改。
- **4 紧急补货 / 导出**：弹窗固定打开瞬间的清单，推荐量 `max(0, ceil(正常库存 × 80% − 预计库存))`；「保存 Excel」只作下载副本，不当持久化。
- **5 筛选与行选择**：关键词 + 四色多选（同类为或、跨维为且），父行只在有匹配子行时显示并按可见子行重算，计数仍按全量 SKU。
- **6 需安排草稿与采纳**：需安排先存草稿、只做浅色预览，采纳才写入并锁定，撤销回滚原值；采纳与紧急补货同写采购清单。
- **7 边界**：计算与预警以颜色 SKU 为单位，父行只汇总；未采纳草稿不参与正式计算。
- **8 验证方式**：每轮 `npm run build` + 浏览器实测，此后不再逐条罗列。
- **9 库存分层**：在仓 / 在途 / 理论库存，在途 = 需安排 + 生产中、理论 = 在仓 + 在途；预警、缺口与紧急补货改按理论库存计算。
- **10 品名列独立**：品名与颜色拆两列、品名固定最左，父行在品名列折叠、子行重复显示品名。
- **11–12 示例面板与导航分组**：示例面板复用同一套组件、按 `panelKey` 隔离数据；导航抽成共享组件（示例面板于第 74 条整体删除）。
- **13 Excel 导入与 3 万行性能改造**：按「品名 + 颜色」整表替换、确认前预览逐行报错；表格改自研虚拟化 + 单行缓存增量刷新，3 万行导入 33.2s → 1.55s、DOM 103 万 → 约 1400 节点、堆 2.29GB → 约 130MB（见[主面板性能优化](./主面板性能优化.md)）；配置页超 500 行改扁平分页。

## 二、库存口径与全面板（14–24）

- **14–15 预计库存**：在途改为导入项，理论 = 在仓 + 在途；再把需安排接回为评估层——预计库存 = 理论库存 + 需安排，预警 / 缺口 / 紧急补货按预计判定，理论库存不被改写；列序定为在仓 → 周转入 → 在途 → 理论 → 预计，导出多一列、导入忽略该列以防重复计数。
- **16–17 紧凑化**：行高 44 → 34px，列宽 `minmax(宽度px, 宽度fr)` 按比例分摊；移除「加入商品」，新增只能靠导入；配置页品名 / 颜色拆两列与主面板对齐。
- **18–22 全面板（只读全量视图）**：两级结构（品名汇总 + 颜色折叠）、数字列自动参与汇总、默认按品名聚合月均降序排序，3 万行约 0.33s 可交互；评分因子收敛为 4 个动销指标并调整热销A 默认阈值。
- **23–24 销售表与双文件导入**：`/all` 改 `/sales`，列固定为品名 / 颜色 + 动销指标 + 1-12 月条数与重量；导入改为「总表 + 销售表」按表头自动识别角色，销售表 4 个动销指标写回主面板重算评分，整表替换抽到 `inventoryApply.js`。

## 三、备货策略配置化（25–30）

- **25 模式 → 评分档 → 系数**：新增自包含模块 `src/stocking/`（字段 / 默认值 / 校验 / 引擎）；模式因子定归属 → 每条模式自选评分因子与 S/A/B/C 阈值 → 档位取系数；开发态写回 `config.json` 并屏蔽其 HMR；SKU 键改为「唯一标识」。
- **26 修复保存配置后主面板仍用旧模式**：派生字段改为渲染时按当前配置现算，store 与导入不再存快照。
- **27 防误删与撤销 / 重做**：删除两段确认（3 秒内再点生效），其余操作靠撤销兜底（JSON 快照、600ms 合并、栈深 50、支持快捷键）。
- **28–29 修复改名后系数全「缺省」**：`evaluate()` 直接返回命中档位系数，行数据带 `strategyIssue`；四列缺省改显示短原因，悬停看完整说明。
- **30 唯一标识不再作为界面列**（导入模板与导出仍保留以维持关联）。

## 四、清洗引擎与配置页（31–39）

- **31 导入分表**：一次多选 5 张分表、按文件名认领、缺一张不允许开始；清洗在 Worker 执行并回传进度，出入库明细（约 150MB）改流式逐行解析。
- **32–33 口径收敛到单一引擎**：清洗口径抽到 `tools/cleaning/engine.mjs`，网页侧只剩一行转发、脚本直接 import；该目录成为构建依赖，不可删除或改名。
- **34–35 SKU 弹窗与术语**：颜色单元格 ⓘ 打开 `SkuDetailDialog.vue`，现算模式 / 系数、因子等级与 1-12 月图（ECharts 按需引入，主包 1.09MB → 559kB）；术语统一为「评分档 / 评分因子」，导入同时认旧表头。
- **36–39 策略层与配置页交互**：配置升 v2，`rules` 改 `strategies[]`（自动 / 手动），手动清单单独存 `manualSkus.json`、评估命中即短路；策略单选移到弹窗标题行；修复数值输入失焦还原；配置页次要按钮靠左、确定靠右并补悬停说明。

## 五、批量补货、只读化与多方案（40–48）

- **40 批量补货**：首列复选框 + 表头全选（只作用当前筛选结果）、品名父行全选 / 半选，选择只存 SKU 标识、虚拟滚动不丢；底部浮动条 → 确认弹窗（默认量取 `getSuggestedPlanned`）→ 统一经 `applyRestockPlans` 覆盖写「需安排」，紧急补货先换算成绝对量再走同一函数。
- **41 导入值全部只读**：品名 / 颜色 / 库存 / 销量等一律纯文本，面板内的改名与数值编辑入口删除，要改数据就重新导入或改源表。
- **42 指标扩容**：累积条数 = Σ出库数量 ÷ 换算系数，月均条数 = 累积条数 ÷ 动销月份，周消耗 = 月均条数 ÷ 4（语义变化，系数需重校）；新增每月订单数，Σ 月度订单数 = 订单总数。
- **43–44**：弹窗「色彩」移到标题行并按色调区分（黑白灰阶、彩色低饱和彩虹）；主面板整行点击即勾选，品名父行等于整组全选 / 全不选。
- **45 多方案**：配置升 v3（`{ version, activeProfileId, profiles[] }`），方案栏切换 / 复制 / 重命名 / 删除 + 整份导入导出；「按当前数据校准」取非零值分位（S≈p90 / A≈p70 / B≈p40），只改草稿。
- **46–48 客户指标**：出入库明细新增可选「客户」列（去重计数），缺列整列为 0；新增「客户CR5率」（前 5 客户销量 ÷ 总销量，只在销售表按比例展示、父行按累积条数加权平均）；「动销客户」改名「累计客户」并保留旧表头别名。

## 六、需求 1.5：模式与评分（49–58）

- **49 模式重构**：改为「月均条数 → 5 个固定模式（热销 / 常规 / 按量 / 尾货 / 滞销）→ 系数」，热销与常规比日库销比、按量比库存条数，尾货 / 滞销 / 专属品只标注不取系数；库存与销量统一换算成条（1 条 = 100 码 = 20 公斤）；加权月销量 = 近 1 月 ×50% + 近 3 月月均 ×30% + 近 12 月月均 ×20%（可改，须合计 100%）；配置升 v4、旧配置整份丢弃；主面板删评分档 / 等级列、新增「日库销比（天）」。
- **50 5 维健康度评分**：客户 CR5 / 累计客户 / 销售环比 / 本次进销比 / 预估月消耗各配区间与权重，综合 50~70 为中风险；建议补货改 `ceil(正常库存 − 理论库存)`。
- **51 评分设置独立成组件**：每个维度改低 / 中 / 高三条区间（端点留空表示不限，同落两档按中 → 高 → 低取第一条命中）；修正本次进销比方向。
- **52 SPU 分级**：品名父行按月均条数合计分 S+ / S / A / B / C / Z（≥2500 / ≥300 / ≥100 / ≥30 / ≥1 / 其余），与 SKU 级模式互不影响，阈值存 `spuGrades.tiers`。
- **53 配置页重排**：「吸顶工作条 + 模式工作区（左列表 / 右编辑）+ 三张折叠卡片」，长说明收进 ⓘ，删掉结果表，页面高度由 7280px 收进一屏。
- **54 模式判定改区间** `range { from, to }`，按顺序取第一条命中，落空档退回「下限最高且不高于该值」的模式。
- **55 按量模式也分流专属品**：累计客户 = 1 时标「按量·专属品」，不取系数、不参与计算。
- **56 弹窗月度订单数图默认折叠**（纯 CSS 过渡），关弹窗复位。
- **57 出码率接入、统一公斤口径**：码 ÷ 出码率 = 公斤，无法换算的 SKU 在基准表阶段剔除；三档 / 缺口 / 建议量全按公斤，删除条换算系数；销售表每月「条数 / 销量(公斤) / 订单数」三列 + 累积销量，评分同步改公斤口径。
- **58 按量模式的健康度定制**：改「本次进销比（<40% 低 / 40%~60% 正常 / >60% 高）」+「累计客户数（<5 高 / 5~10 中 / >10 低）」两项判定、不算综合分，阈值存模式 `healthScoring`，规则文案随阈值生成。

## 七、手动策略（59–62）

- **59 手动「滞销模式」改名「排除模式」**（`slow` → `exclude`）：不计预警、不进紧急补货、不给建议值，仍可人工填需安排；旧配置与旧手动清单自动迁移。
- **60–61**：手动「自定模式」改名「自定系数模式」；新增「订单货模式」（`order`），不参与预警与评分，需安排填多少就下多少。
- **62 销售环比按系统日期取月**：≥26 号比「本月 vs 上月」，≤25 号比「上月 vs 前月」；缺月、上期为 0、两期都为 0 各有专门文案。

- **66–69**：空行不再被归一化丢弃（`keepBlankEntries` 运行时开关）；`settings.json` 升 v2 新增独立分单人员表；分类改「分类下拉 + 人员勾选」；分类未分配人员时回退到人员表全部。
- **70 屏蔽 SKU / 品名**：写 `src/stocking/hiddenSkus.json`，只影响主面板展示（行、父行合计、计数、批量与紧急补货、导出），源表与销售数据不动；解除在 `/hidden`。

- **73 缸规则初版**：`settings.json` 升 v3，规则 = 判据 + 分档（`skip` / `fixed` / `vat` / `round`），需求 > 0 时至少 `minVats` 缸；缸只作用于下单，不改需安排与建议值。
- **74–75**：删除示例面板与 `panelKey`；屏蔽列表抽成独立页 `/hidden`（分组树、多选、逐个 / 全部解除、搜索）。
- **76 删除手动「排除模式」**：旧方案文件里的 `exclude` / `slow` 模式加载时丢弃，旧手动清单记录随之清除（SKU 回到自动策略）。
- **77 缸规则改为「按缸型就近取整」**：一个 SKU 是一组缸型（如 80 / 160 / 240），就近取整、正好一半向上、超最大缸取模、最少 1 缸，临界点（120 / 200 / 360）由缸型推导而非手写；不拼缸，一张分订单只用一种缸型；下单页缸数只收整数，非整缸只提示。
- **78 分订单默认带值**：`addEntry()` 用缸规则对「需安排 − 已下单」换算并带出公斤与缸数，染厂 / 人员沿用上一张；进面板或「去下单」弹窗时也自动带一张（同一 SKU 只带一次，删掉不再补），「按建议添加」按钮删除。
- **79 「状态」改「下单数量」+ 新颜色口径**：颜色收敛到 `src/purchase/fillTone.js`——未下单灰 → <80% 黄 → 80%~100% 绿 → 超一缸内绿 → 超过一缸红，列表、右面板进度、底部差额与弹窗共用。
- **80 采购下单页排版**：左栏 322 → 460px、品名 / 颜色拆两列、数字居中；列表撤销改两段式（首点变「确认撤销」，点别处取消，⋯ 菜单仍弹窗确认）；颜色规则收进悬停，不再占版面画图例。

## 十九、演示数据按真实模式分布重造

问题：第十八节的演示数据导入后整张表都是「尾货·不参与」，评分 `—`、需安排全 0，预警与下单流程没法体验。原因是造数口径，不是系统判定：

- 月销量只给了 5~124 公斤，按「1 条 = 20 公斤 / 100 码」折算不到 1 条/月；
- 而且只有 7 天出库数据，`动销月份` = 1，月均条数被再压到 1/4；
- 两者叠加，几乎所有 SKU 都掉进「尾货 0.01~3 条/月」，少数四舍五入成 0 条的变「滞销」。真实 22k SKU 的分布其实是 尾货 73% / 按量 15% / 常规 6% / 热销 2% / 滞销 3% —— 尾货占多数是业务事实，但演示数据一个可参与备货的都没有，就没法验收。

改法（`tools/cleaning/simulate-rolling.mjs`）：

- **先定月均条数目标再折公斤**：`MODE_BANDS` 按真实比例给五档权重，区间取在 `config.json` 各模式范围内且远离端点；再按「20 公斤/条」或「100 码 ÷ 出码率」折成月销量。
- **历史横跨 3 个自然月**：预置 `8/1~10/24` 出库（每 SKU 约 10 笔大单），回放窗口改成 `10/25~10/31`，`动销月份` = 3，月均条数才等于设定的目标值。
- **在仓按 0.5~3 个月的销量铺开**：预警灯红 / 黄 / 绿 / 紫四档都有人；下限 0.5 个月是为了盖住窗口期的出库量。
- **场景 SKU 只在历史里出库**：在仓 7 天不动，`1500 不跳` 的剧本数字才核对得清；月均条数 70（热销），需安排可填、预警不再是「不参与」。
- **客户按笔轮换**：每 11 个 SKU 留一个单客户专属品（模式名带「专属品」、不参与备货），其余多客户，避免全部被判成专属品。
- 新增断言：可参与备货的占比落在 20%~50%、需安排建议 > 0 的 SKU ≥ 20 个、预警灯覆盖四档、场景 SKU 必须参与备货。

结果（120 SKU 演示数据 D7）：热销 14 / 常规 16 / 按量 26 / 尾货 65 / 滞销 7，紧急补货 20 / 常规补货 14 / 无需补货 7 / 降低库存 12 / 不参与 75，需安排建议 > 0 的 30 个；1000 SKU × 7 天回放 21,266 项断言全绿。演示数据重造为 4.3 MB（历史出库笔数决定体积）。

顺带修：`--no-files` 之前根本跑不通（回放要读磁盘上的 xlsx，不落盘就直接报缺文件），改为落到临时目录、跑完删除；重跑只清 `day-*` 子目录，不再连 README 一起删。

## 二十、理论库存改用对账后的在途

现象：导入 day-03 后 `场景A品/1#黑` 在仓 1500、在途 0，理论库存却是 2000；场景B 1240 + 在途 240，理论 1720；场景C 1600 + 在途 0，理论 2200。

原因：`calculateInventoryRow` 里 `理论库存 = 在仓 + 生产中`，而「生产中」取的是生产排单的**原始累计**（`producing`）。排单是只增不减的流水 —— day-03 的文件里 D2 那行 500 还在，所以入库之后这 500 仍被算一遍；而主面板「生产中」列显示的是对账后的 0/240，虚出来的那部分在界面上根本看不见。上一轮把预计库存切成「在仓 + 在途 + 需安排」时漏了理论库存这一列。

- **口径**：`理论库存 = 在仓 + 在途`（= 预计库存 − 需安排），与「在途 = 已安排 + 生产中」同一套；没有对账值（旧调用方）时退回「在仓 + 生产中」。
- **连带变化**：评分的「预估月消耗」用 `理论库存 + 建议需安排`，现在正好等于预计库存；`getSuggestedPlanned` 在新口径下就是 `正常库存 − 理论库存`。
- **验收**：回放新增断言「理论库存 = 在仓 + 在途」，1000 SKU × 7 天 28,322 项全绿；`check-stocking` 全绿、`npm run build` 通过；浏览器导入 day-01→03 实测 场景A 1500/1500/1500、场景B 1240/240/1480（在仓/在途/理论）。

## 二十一、上线可用性核对 + 快照名额 5 → 14

## 二十四、分订单种子清空 + 订单存储归属

背景：新开一个浏览器（新 origin，如 `localhost:5173`）导入 day-01 后，「已下单」显示 16 个 SKU —— 那不是缓存串号，而是 `src/purchase/orders.json` 里的**演示订单**：种子随 bundle 静态导入，`loadOrders()` 在没有任何本机数据时直接吃它；更麻烦的是开发态 `saveOrders()` 会把真实订单写回同一个文件，于是「出厂种子」变成了跨 origin 共享的数据总线（last-write-wins）。

- **清空种子**：`src/purchase/orders.json` 置为 `{ version: 2, updatedAt: '1970-01-01T00:00:00.000Z', drafts: {}, orders: [] }`。时间戳必须留在 epoch —— 三层来源（种子 / localStorage 副本 / IndexedDB 文档）按 `updatedAt` 抢最新，空种子若带当前时间会把本机真订单反向覆盖。
- **开发态回写改道**：`vite.config.js` 的 `PURCHASE_ORDERS_FILE` 指向 `src/purchase/orders.dev.json`（路由 `/__purchase-orders/save` 不变），并加进 `.gitignore`。这份镜像不参与启动读取，仅供调试时看 JSON。
- **存储归属不变**：订单 / 草稿继续以 IndexedDB `documents.purchaseOrders` 为准（整份 v2 文档，几十 MB 级；localStorage 只留 ≤ 1 MB 副本，超限即删）。本次只拆掉「种子会被写脏」这条耦合，介质不动 —— 订单是运行时数据，本来就不该进仓库。
- **清掉已污染的本机数据**：旧 origin 在启动时已把种子订单复制进 IndexedDB，改种子不会自动回滚；在下单历史里「删除批次」或「清空本机数据」即可归零。
- 验证：新 origin（`127.0.0.1:5173`，与本机 `localhost:5173` 不同源）打开即「已下单 0」；`npm run build` 通过。

## 二十五、预警灯绿区上沿改成峰值

背景：主面板给一个本来**绿**的 SKU 填需安排，灯直接变**黄「常规补货」**。原因是 `getUrgency()` 的兜底分支把两个不相邻区间合并成了一盏灯 —— `[红线, 正常×0.8)` 是"还没补够"，`(正常×1.2, 峰值]` 是"已经补过头"，都叫「常规补货」。而需安排会直接进预计库存，所以加量必然把指标往上推：绿 → 黄（右段）→ 紫，方向读反了。

- **判据调整**（`src/utils/inventory.js`）：`< 红线` 红、`> 峰值` 紫、`≥ 正常 × 80%` 绿、其余（红线 ~ 正常 × 80%）黄。绿区上沿从「正常 × 120%」放到「峰值」，黄只剩"补不够"一种含义，加量单调变好（红 → 黄 → 绿 → 紫）。
- **连带口径**：`src/stocking/replenishRisk.js` 的「日库销比」因子直接吃 `urgencyTone`，在此区间内从「偏离 / 中」变成「正常带 / 低」；它的正常带文案也跟着改成 `正常×80% ~ 峰值`。
- **示例**（热销·彩色 15/30/45，日销量 35 公斤，理论库存 1000 公斤 = 28.5 天）：绿区 842 ~ 1578 公斤（需安排 ≤ 578），之前需安排超过 262 就变黄，现在到 578 才变紫。
- **自检**：`tools/check-stocking.mjs` 新增「常规·偏多（40 天 → 绿）」与「常规·超峰（50 天 → 紫）」两个样例，锁住绿带上沿与新分支；现有 5 档样例不受影响。
- **文档**：模式与系数设置 4.3 / 4.4、PRD-系统现状 6.5、列头悬停补一行「区间」；§13 的 2026-11-10 验证记录保留并标注为新口径下的差异。
- 验证：`node tools/check-stocking.mjs` 全绿、`npm run build` 通过。

## 二十六、采购状态改成订单时间轴（已下单 / 已到仓）

背景：按「每天导昨天的分表」滚动用下去，day-1 下 500 公斤 → day-2 排单出现、已安排转生产中 → day-3 出入库出现生产入库、在途归零。此时「生产中 / 已安排 / 在途库存」全回 0，行已经是一个普通的 SKU、只等下一次预警，但筛选条上的「已下单」还挂着它 —— 因为那个 chip 上的判据是「累积下单 > 0」，而累积下单是只增不减的累计值，货进仓以后照样命中。

- **「已下单」改看当前在途**：命中 = 下过单（`row.ordered > 0`）且还没到仓（`row.inTransitKg > 0`）。只看在途不够 —— 第一次导入的排单表里可能本来就有产量（提前备货 / 外面下的单），那批货不是「我们已下单」，所以两个条件都要。
- **新增「已到仓」chip**：命中 = 下过单且已全部到仓（`ordered > 0` 且 `inTransitKg = 0`）。这一档正是「这个品下过单」的记录：货到齐了回到普通 SKU 等下一次预警，但想回看时点它就能列出来。三档（下单中 / 已下单 / 已到仓）互斥，store 里对应 `onlyOrdering` / `onlyOrdered` / `onlyArrived`。
- **行级留痕**：`在途库存` 格右侧的采购订单图标仍按「有未作废订单」显示；在途归零后图标转灰（`.ordered-detail-button--settled`），悬停写明「下过单（已全部到仓）：累计下单 … · 到货 … · 待收 …」，点开还是同一张订单流水。「累积下单 / 待收 / 到货」三列照旧只增不减，是留痕列，不参与筛选。
- **连带**：列头悬停、`采购下单流程.md` §3.3 的列名（原来还写着「已下单 / 已到货」，与实际三列不一致）一起更正；筛选互斥逻辑（清预警色 / 清其它采购状态、`hasActiveFilters`、`isAllFilterSelected`、`resetFilters`、滚动回顶）都把第三档接上。
- 验证：`npm run build` 通过；在 2 万 SKU 的演示 origin 上把某个 SKU 的 4 张分订单逐张登记到货 → 「已下单 16 → 15」「已到仓 0 → 1」，行尾图标转灰；随后逐条撤回到货 → 回到 16 / 0，数据无残留。

## 二十七、采购执行层收敛（删备货三列）+ 新增「SKU 数据变动」

背景一：滚动导入跑起来以后，主面板的「累积下单 / 待收 / 到货」经常自相矛盾 —— 同一个 SKU 显示「待收 500、到货 0」，可「在途库存 = 0、在仓库存 1500」，货明明已经进仓了。原因是「到货」只统计**手工登记**的 `receipts`，而到仓事实来自导入的出入库明细；两套口径并存，`待收` 必然越走越偏。另外导入只有 SKU 级生产入库，**还原不出「每张分订单各自到了多少」**，按单勾到货在滚动模型里永远填不准。

背景二：主面板是全量数据，每次导入后「今天到底变了什么」看不出来 —— 只能靠记忆逐行比对。

- **删「备货」分组**：`TABLE_COLUMNS` 去掉 `pending` / `received` 两列，`ordered` 改名「下过单」并入「入口」组（紧跟「已安排」）；连带删掉可折叠大表头的 `isStockingGroupExpanded`、`stockingGroupPlaceholder` 占位列与 `.stocking-group-toggle` 样式。判断到没到仓只看「在途库存」，`下过单` 只作留痕（只增不减）。
- **弹窗改成只读对账**：[`PurchaseOrderRecordsDialog.vue`](../../src/components/PurchaseOrderRecordsDialog.vue) 重写为「分订单明细」——列头左「N 张 · 下单合计」右「到仓对账 在仓 X · 在途 Y」，行内只有染厂 / 人员 / 时间 / 下单公斤（按缸的带缸数）；`⋯` 里保留 **改单 / 补登记到货 / 撤销整单**。右侧「到货记录 + 登记到货 + 撤回·恢复·删除」整块下线（数据仍写 `receipts`，只是界面不再展示）。
- **补登记到货**是兜底：导入还没跟上、或「来源单据」名称没匹配上时，用它可以提前扣在途；它**只动在途、不动在仓**，上限 = 该单剩余。
- **新增「SKU 数据变动」**：`applySourceImport()` 在整表替换前 `captureImportBaseline()` 抓旧值，替换后 `buildImportDiff()` 逐字段比一次，`saveImportDiff()` 落 `documents.importDiff`（最近 6 份，只存变动的行）。每次导入后**自动弹出** [`ImportDiffDialog.vue`](../../src/components/ImportDiffDialog.vue)，页头「数据变动」按钮可回看历史批次。
  - 比的字段：在仓库存（公斤）/ 周销量 / 生产排单累计 / 生产入库累计 / 退货入库累计 / 欠货 / 周转入 / 公斤系数 + 品名颜色（改名）。派生值（理论库存、预警灯、建议需安排）**不存**，避免换配置后历史失真。
  - 弹窗：`当前 N 个 SKU · 有变化 / 新增 / 消失 / 未变` + 九个 chips（全部 / 有变化 / 新增 / 消失 / 在仓 / 周销量 / 排单 / 入库 / 改名）+ 关键词，明细一行一个 SKU 铺 `字段 旧 → 新 (+差值)`；只渲染前 200 行，「导出 Excel」拿全量（`saveWorkbook`）。
- **验证**：`npm run build` 通过；新 origin（`:5177`）导入 `docs/测试数据/滚动导入演示/day-01` → 自动弹出「新增 128 / 消失 1000」（对照种子数据），页头「数据变动」由置灰转为可用；紧接着导入 `day-02` → 「有变化 4 / 未变 124」，4 行全部是「生产排单 0 → 500 / 480 / 600 / 200」，与演示脚本「day-02 排单进场」的设定一致；`:5176` 上打开分订单弹窗，列头正确显示「下单合计 2,880 公斤｜在仓 5,374 · 在途 2,880」，`⋯ → 补登记到货` 提示「最多 1,440 公斤」。
