# 滚动备货策略（每天导入昨天的分表）

> 一句话：**每天导入一次昨天截止的 5 张分表 → 系统把同一批货在「需安排 → 已安排 → 生产中 → 在仓」四个位置之间自动搬一次 → 主面板给出的永远是今天这一刻的最新预警。**
>
> 原则：**一批货只有一个位置、只算一次**。人只做两件事：填「需安排」、在采购下单页拆单确认；位置迁移全部由导入 + 订单流水推导，不靠手工勾。

---

## 1. 业务节奏

| 时间 | 发生什么 | 系统里对应的动作 |
| --- | --- | --- |
| 昨天 | 客户下单 / 染厂排产 / 生产入库 / 仓库收发 | 数据落在那几张分表里 |
| 今天早上 | 生产人员导入昨天截止的分表 | 主面板全量替换，自动重算在途、理论库存、预警 |
| 今天上午 | 看预警 → 填「需安排」→ 采纳 → 采购下单拆单 | 需安排（计划层）→ 分订单（执行层） |
| 明天早上 | 再导入一次 | 「已下单」里的货自动推进成「生产中」，到货后转「已到仓」 |

导入是**全量替换**，不是增量：总表整表换掉，销售表按 `skuId` 重新挂接，需安排 / 订单 / 屏蔽清单按 `skuId` 保留。所以每天**必须导完整的一套分表**，不能只导变更行。

---

## 2. 核心模型：一批货只有一个位置

```
需安排（未下单）  ──确认下单──▶  已安排（下单了、还没排单）
      ▲                              │  导入里出现「生产排单」
      │撤销订单                        ▼
      └────────────────────────  生产中（排单了、还没进仓）
                                     │  导入里出现「生产入库」
                                     ▼
                                  在仓（库存结存表）
```

- **在途 = 已安排 + 生产中**：还没进仓的那部分，无论「我们下过单」还是「染厂已经排上产」都只算一次。
- **谁推进位置**：「已安排 → 生产中 → 在仓」由导入数据推进；「需安排 → 已安排」由人在采购下单页点「确认下单」推进；「撤销订单」把公斤数退回需安排（未锁草稿态）。
- 桶间迁移时**预计库存必须纹丝不动**，否则每天导入预警会反复跳色。

---

## 3. 口径（唯一实现，别在页面里再算一遍）

记号：`o` = 当前有效订单（`status = active`）的下单公斤累计；`s` = 生产排单「进仓重量」累计；`r` = 生产入库累计；`w` = 在仓库存 × 公斤系数。

| 量 | 公式 | 实现 |
| --- | --- | --- |
| 在途 | `max(0, max(o, s) − r)` | [`src/purchase/inTransit.js`](../../src/purchase/inTransit.js) |
| 生产中 | `min(max(0, s − r), 在途)` | 同上 |
| 已安排 | `在途 − 生产中` | 同上 |
| 理论库存 | `w + 在途` | [`src/utils/inventory.js`](../../src/utils/inventory.js) `calculateInventoryRow` |
| 预计库存 | `理论库存 + 需安排（锁定值）` | 同上 |
| 建议需安排 | `max(0, ⌈正常库存 − w − 在途⌉)`（补到绿区下沿） | 同上 `getSuggestedPlanned` |
| 日库销比 | `预计库存 ÷ 日销量`；日销量 = 加权月销量 ÷ 30 | 同上 |
| 预警 | `< 红线` 红 / `< 正常×80%` 黄 / `≤ 峰值` 绿 / `> 峰值` 紫 | 同上 `getUrgency` |

三条容易写错的规则：

1. **取 `max(o, s)` 而不是 `o + s`**：同一批货在「下单」和「排单」两个视角里只算一次；而排单里可能有我们没在本系统下过单的产量（提前备货 / 外面下的单），那也是要进仓的货，所以不能只取 `o`。
2. **减 `r` 而不是「等排单消失」**：排单导出是只增不减的流水，已完成的行不会消失，只有**生产入库**能证明那批货真的进了仓。
3. **退货入库不进 `r`**：退货只让在仓增加，不应该把我们的采购单冲掉（清洗后单独落在 `returnedIn`）。

系数（红线 / 正常 / 峰值的天数或公斤）来自模式判定，见 [模式与系数设置.md](./模式与系数设置.md)；改系数后**所有 SKU 的预警与建议值跟着变**，不必重新导入。

## 4. 切换日基线：为什么第一次导入要「清零重来」

`o` 是系统自己记的（订单流水），但 `s` / `r` 是**导入表里的历史累计**。直接拿来算，历史产量会把在途撑爆（实测某次导入排单累计 21.7 万公斤）。

所以第一次导入（准确说是本机第一次建库）时会记一份**基线**：每个 SKU 当时的 `s` / `r` 值，之后只用增量：

```
s实际 = 导入的排单累计 − 基线排单
r实际 = 导入的生产入库 − 基线生产入库 + 手工补登记
```

- 基线单独存 `documents.inTransitBaseline`，**跨快照保留**（换快照回滚不会把历史产量重新算进在途）。
- 基线只在第一次导入时建；之后每天导入都沿用同一份，增量才会连续。
- 「清空本机数据」或换浏览器 origin 等于重新开始算增量 —— 表现是「在途先归零、需安排建议重新给出」，属于预期行为。

## 5. 一天的完整走查（A 品 · 500 公斤）

| 时点 | 导入里有什么 | 需安排 | 已安排 | 生产中 | 在途 | 在仓 | 预警 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Day1 导入后 | — | 500（建议值） | 0 | 0 | 0 | 1000 | 红（紧急补货） |
| Day1 下单后 | — | 0 | 500 | 0 | 500 | 1000 | 绿（预计 1500） |
| Day2 导入 | 排单新增 500 | 0 | 0 | 500 | 500 | 1000 | 绿（预计仍是 1500） |
| Day3 导入 | 出入库明细有生产入库 500 | 0 | 0 | 0 | **0** | **1500** | 绿（等下一次预警） |

要点：

- Day2 只是「已安排 → 生产中」，`max(o, s)` 没变，预计库存不动，**不会因为导入而跳色**。
- Day3 到仓后这个 SKU 回到普通状态：不再出现在「已下单」，转进「已到仓」；「下过单」那列仍留着 500 公斤当留痕。
- 之后如果又预警变红，走一遍同样流程即可；同一 SKU 可以同时有「旧单还在产 + 新单已下」。

## 6. 主面板上怎么看（采购那条线）

| 位置 | 含义 | 判据 |
| --- | --- | --- |
| 入口 · 需安排 | 今天要补多少（唯一可编辑列，采纳即锁定） | 人的输入；占位是建议值 |
| 入口 · 已安排 | 下单了、染厂还没排产 | `在途 − 生产中` |
| 入口 · 生产中 | 已经排产、还没进仓 | 排单增量 − 生产入库，封顶在途 |
| 入口 · 下过单 | 累计下单公斤（**只增不减，纯留痕**） | Σ active 订单 quantity |
| 库存 · 在途库存 | 还没进仓的合计；到没到仓看它 | `max(0, max(o,s) − r)` |
| 库存 · 在仓库存 | 仓库结存（公斤） | 库存结存表 × 公斤系数 |
| 库存 · 理论库存 / 预计库存 | `在仓 + 在途` / 再加需安排 | 见第 3 节 |

筛选条「采购」组的三个互斥档（按订单时间轴，互不重叠）：

| 档 | 判据 | 用途 |
| --- | --- | --- |
| 下单中 | 需安排已采纳、等待确认下单（`plannedUndoHistory` 锁定） | 还没落地的那批 |
| 已下单 | 下过单（下单累计 > 0）且**还没到仓**（在途 > 0） | 催染厂 / 等货 |
| 已到仓 | 下过单且**已全部到仓**（在途 = 0） | 「这个品下过单」的记录，到仓后回普通状态 |

- 「在途库存」格右侧的行尾图标：有未作废订单就常显，点开是**分订单明细 + 到仓对账**；在途归零后图标转灰。详见 [采购下单流程.md](./采购下单流程.md) 3.3 / 3.4。
- **小额补货门槛**（设置 → 备货配置 → 筛选显示规则）：紧急 / 常规两档里建议值不足门槛的 SKU 默认不列（几公斤不值得开缸），门槛只影响这两个 chip 的计数与筛选，数据一行不动。
- **紧急补货**按钮给的永远是全量清单（不受筛选影响），弹窗里写清排除了多少个。

## 7. 每次导入后：「SKU 数据变动」

主面板是全量数据，看不出「今天变了什么」，所以每次导入后自动弹一份差异汇总（页头「数据变动」按钮可回看最近 6 次）：

- **比什么**：在仓库存（公斤）、周销量、生产排单累计、生产入库累计、退货入库累计、欠货、周转入、公斤系数，外加品名 / 颜色（改名）。
- **不比什么**：理论库存、预计库存、预警灯、建议需安排 —— 这些跟着配置变，存进历史会失真。
- **怎么筛**：`全部 / 有变化 / 新增 / 消失 / 在仓 / 周销量 / 排单 / 入库 / 改名` + 关键词；只渲染前 200 行，「导出 Excel」拿全量。
- 实现：[`src/data/importDiff.js`](../../src/data/importDiff.js)（抓旧值 → 比对 → 落 `documents.importDiff`），界面 [`ImportDiffDialog.vue`](../../src/components/ImportDiffDialog.vue)，口径见 [前端视图与交互.md](./前端视图与交互.md) 6.1。

## 8. 数据落盘与容量

| 层 | 存哪 | 保留 |
| --- | --- | --- |
| 事实层（导入的库存行 + 销售表） | `snapshots`（gzip） | 最近 **14** 份，内容哈希相同只更新时间 |
| 计划层（需安排 + 撤销快照） | `meta.workspace`（按 `skuId`） | 一直保留 |
| 执行层（分订单 + 草稿） | `documents.purchaseOrders` | 一直保留 |
| 对账层（切换日基线） | `documents.inTransitBaseline` | 不随快照回滚 |
| 报表层（SKU 数据变动） | `documents.importDiff` | 最近 **6** 份，只存变动的行 |

2 万 SKU 的一份快照压缩后约 **2.4 MB**（128 SKU 约 10 KB），14 份加起来 30~35 MB 量级；订单文档几百 KB 到几 MB。「SKU 数据变动」只存变动的行，通常比快照小一个量级。空间不够时先删旧快照或导出 xlsx 留底，明细看「设置 → 数据 → 本机数据存储」。细节见 [数据持久化方案.md](./数据持久化方案.md) 第 10 节。

## 9. 已知边界（用之前要知道）

1. **到仓只认「生产入库」类来源单据**：清洗引擎按 `生产入库 / 加工入库 / 生产进仓 / 加工进仓` 匹配；厂里换成别的写法，在途就不会归零。处理办法：改清洗规则，或临时在分订单明细 `⋯ → 补登记到货` 兜底（只扣在途、不动在仓）。
2. **退货入库不算到仓**，只加在仓库存。
3. **提前备货 / 外部下的单**：排单有量、本地没有订单 → 在途 > 0，但**不算「已下单」**（这一档要求下单累计 > 0）；它会在「生产中」列显示出来。
4. **基线之前的产量不算在途**（见第 4 节），所以切换日当天的在仓是起点，不是历史累计。
5. **在途是总量**：一个 SKU 同时有多批货在途时，系统只给合计，不区分哪一批；分订单明细只到订单级。
6. **分订单级到货还原不出来**：导入只有 SKU 级生产入库总量，因此「每张分订单到了多少」不可维护，界面上已下线按单登记到货。
7. **每天全量替换**：只导增量表会让后出现的 SKU 消失、需安排挂空。
8. **缸只在采购下单环节生效**：需安排与建议值始终是精准公斤，不取整；同一张分订单只用一种缸型，不拼缸。
